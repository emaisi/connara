## 1. 已确定的决策

采用 React Flow 开源核心（`@xyflow/react`）、按需引入的 React Flow UI 组件、Dagre 自动布局、Connara 现有 React/Tailwind/Radix UI 和 Go 工作流执行器。

不依赖 React Flow Pro 付费模板。React Flow UI 按源码组件使用，接入时核对所复制文件的许可并保留必要声明；不要把“核心库开源”理解为所有 Pro 内容都可自由复制。

先以阶段零验证关键交互，再将编辑配置和运行追踪分为两个工程阶段推进；它们共同构成本次完整交付，不能只完成画布就宣布完成。

核心原则：

1. 版本化的 `graph` 是唯一执行定义，保留 `steps + output`，v2 增加输入 Schema、步骤类型和分支作用域；画布与连线由它派生，不保存第二套执行图。
2. 依赖连线与参数映射分别表达，不把连线误解释为自动传递整个响应。
3. 复用 API 定义、执行目标、账号验证、运行事件与加密快照；不引入第二套执行引擎。
4. 编辑布局独立于业务版本保存，拖动节点不能让已部署工作流停止定时运行。
5. 历史画布使用当次运行快照，不根据今天的工作流或 API 定义重建历史事实。
6. UI 主流程使用“API、集成、账号、输入参数、条件分支”等业务名称。connectionKey、scope 等内部字段只在高级配置和开发文档中出现。
7. 业务保存继续沿用“回到草稿、停止新的触发”的现有语义，界面必须提前说明影响；本次不自动保存业务配置。草稿与部署版本并存属于后续独立扩展，不作为已支持能力。
8. 原始开始输入 trigger 与本次可变流程变量 vars 分开；更新变量只影响本次运行，读写顺序由依赖确定，不能依赖画布位置或无依赖步骤声明次序猜测最新值。

### 1.1 为什么选这套组合

| 维度 | 决策理由 |
| --- | --- |
| 开源 | React Flow 核心 MIT、Dagre MIT；不把付费模板作为必要依赖 |
| 美观 | 用公开节点组件作为基础，沿用现有设计变量、按钮、表单与图标，避免工作流页面成为另一套产品 |
| 简单 | 搜索添加 API、默认串联、侧栏配置和字段选择，让普通流程无需编写 JSON |
| AI 开发 | 普通 React 组件和 TypeScript 函数便于逐文件审查、测试与修改；这是工程判断，不是框架对 AI 的性能承诺 |
| 接入成本 | 将当前依赖、条件、模板映射到画布，保留 Go 引擎、任务队列、调度与权限 |
| 运行体验 | 同一套节点可显示运行状态，业务事实来自后端，不使用动画模拟执行 |

FlowGram 的表单、变量和运行 Demo 更完整，但需要适配插件体系、变量模型和运行客户端，并统一其 Demo UI。Connara 已有相应执行与校验逻辑，因此本项目优先选择更薄的编辑层。后续出现循环、子流程等实际需求时再扩展，不预建通用框架。

### 2.2 已有能力与限制

- 图定义已包含 API 步骤、`dependsOn`、`runIf`、`onError`、输入模板和最终输出映射。
- 步骤最多 20 个；执行定义最多 256 KiB，触发输入最多 64 KiB。
- 单步骤默认预算 40 秒，并受 API 自身配置的更小预算约束；异步运行总预算为 15 分钟。
- 引擎按稳定拓扑顺序串行执行。多个可执行步骤按照定义次序处理，不进行并行调用。
- `runIf` 支持 eq/ne/gt/gte/lt/lte/exists/not_exists 和 all/any；组合最多两层组嵌套、最多 8 个叶子条件，以 Go 校验为准。
- 条件不满足产生 skipped。`onError=continue` 仅容忍确认失败；unknown 仍立即停止。
- 重试策略固定 `maxAttempts=1`，不能展示自动重试、失败节点重跑或断点续跑按钮。
- 空响应是 null，非 JSON 响应是字符串；步骤输出直接对应上游响应，不保证存在 `data` 包装。
- 整值 `{{path}}` 保留 JSON 类型；混合文本只允许标量插值。`{{?path}}` 仅允许最终输出，路径不存在时结果为 null，并非自动删除输出字段。
- 默认触发输入仅在省略运行输入时使用；显式传入的对象替换默认对象，不做深度合并。
- 当前工作流保存会将状态设为 draft 并清空 next_run_at；部署、暂停也会增加 version。
- 已有加密运行快照固定步骤、API 版本、绑定和触发输入。它不是现成的管理端画布查看接口。
- 当前步骤事件在完成时记录 stepId、status、httpStatus、error 与最大 4 KiB 的脱敏响应摘要；摘要来自成功步骤的 Output，响应检查失败会提前返回，失败响应体没有进入现有事件。没有开始事件、步骤耗时和已解析输入摘要。
- 当前运行详情返回 events 数组；因此初版不需要另外建设 SSE/WebSocket。

### 2.3 已确认的接入缺口

| 缺口 | 影响 | 本次处理 |
| --- | --- | --- |
| 大弹窗里逐项编辑步骤 | 流程结构不直观、操作区拥挤 | 独立编辑页和侧栏 |
| 前端草稿保存也要求完整绑定 | 与后端允许未完成绑定的草稿规则不一致 | 草稿可保存未绑定 API 节点；部署前严格校验 |
| 依赖与组合条件以手写为主 | 操作门槛高 | 连线和受限条件编辑器 |
| 根据全局列表及集成名称关联账号 | 可能遗漏分页数据、误匹配或拒绝无认证 API | 使用已有 execution-options，按 ID 和 requiresAccount 处理 |
| 没有持久化布局 | 每次打开图位置变化 | 独立布局列和布局版本 |
| ResolveWorkflowBindings 重序列化 Definition | 放在 graph 的额外 nodes/positions 字段会丢失 | 布局不混入执行 graph |
| 历史快照未向画布提供展示投影 | 工作流或 API 改动后无法准确展示历史 | 新增受限运行视图接口 |
| 列表参数解析 WorkflowID，但 ListOperations SQL 没有该过滤条件 | 历史列表可能混入其他工作流 | 在现有 SQL 中落实 workspace + workflow_id 过滤 |
| 只有完成事件 | 无法准确显示正在执行的节点和耗时 | 补共享开始/完成事件契约 |
| 部署、运行不接受界面看到的版本 | 用户可能运行另一个成员刚修改的配置 | 增加 expectedVersion 校验 |
| 管理端支持按 UUID 查 API，runtime 发现/预检却直接比较 graph.action 与 actionKey | UUID 或系统限定 key 可能部署成功但无法被 runtime 发现/执行 | 先解析同一 API 实体，再使用现有 actionKey 权限契约检查 |
| 工作流校验主要返回错误文本 | 无法稳定完成节点和字段定位 | 增加小型结构化诊断，复用已有参数 FieldError |
| 失败响应未保留到步骤事件 | 运行失败时缺少上游错误详情 | 单独记录限长脱敏响应摘要，不将失败响应作为步骤成功输出 |
| 仅有 API 步骤与单步 runIf | 无法完成列表处理、多出口条件和整条分支隔离 | 新增 transform/condition 执行类型，支持 IF/多 ELSE IF/ELSE |
| 没有分支作用域与按分支来源 | 未执行分支的缺失字段可能导致公共后续失败 | 显式 scope、结构化汇合、命中分支来源懒解析，详见节点专项设计 |
| 没有工作流输入 Schema | UI 类型声明无法约束外部调用输入 | 新增可选 graph.inputSchema，所有触发入口共用验证，兼容旧定义 |
| 没有可变运行变量 | 开始 orderId 无法被 API 返回值更新供后续统一读取 | graph.variables + 节点/出口 assign；初始化、顺序校验、一次提交，保留原始 trigger |
| 没有代码执行能力 | 多个节点共同运算、复杂结构关联无法只靠模板完成 | 增加 code 类型、显式输入/输出 Schema、受限独立 goja worker 和样本执行；详见代码专项 |
| Runner 每次运行新建，服务支持多角色 | 每次新建代码限流器会放大并发；API 本地健康不能代表后台 | main 初始化单例 CodeRunner 并注入 HTTP/后台，逐角色验证能力 |
| 部署 handler 在审计事务内，审计序列化整工作流 | 子进程编译拖长事务；code 字符串可能原样进入审计 | 编译移出事务，提交阶段保持部署/审计原子；审计用专用白名单摘要 |

以上为源码结论，未用浏览器验证现有页面，不把问题推断写成已复现的浏览器缺陷。

## 3. 完整交付范围

### 3.1 必须交付

1. 工作流列表 → 新建/编辑 → 保存草稿 → 部署 → 运行 → 结果 → 历史查看的完整流程。
2. 开始/API/数据处理/代码/条件判断/结束六类节点，节点添加、复制、删除、分支连线与汇合、自动布局、缩放、适应画布、撤销重做。
3. API/集成/账号选择；按 Schema 配置输入；引用触发输入和上游字段；JSON 高级配置；运行输入复用开始节点表单。
4. IF/多个 ELSE IF/ELSE、列表筛选/排序/截取/计数/字段投影、按分支取值、API 失败处理、最终结果映射及部署前定位。
5. 真实步骤状态、耗时、脱敏输入和响应摘要、错误、最终结果与历史版本画布。
6. 老工作流、老运行记录、无认证 API 和缺少 Schema 的兼容。
7. 桌面、窄屏、键盘、离开保护和角色权限；跨路由恢复编辑、保存期间继续编辑及 20 步流程导航。
8. 定时配置的常用选项、明确时区和服务端计算的未来三次计划时间预览。
9. [十个常用场景](workflow-node-design.md#scenarios)与[五个稍复杂场景](workflow-node-design.md#advanced-scenarios)逐项验收；批量同步仅在目标有批量 API 时纳入成功路径。
10. 流程变量声明、初始化、API/处理后及条件出口赋值、共用读取选择器、按返回值选择不同加工、样本赋值预览与运行变更追踪。
11. 只读运行信息的来源选择、快照/样本一致性；代码正式执行与交互容量分配；能力关闭期间的调度跳过和恢复时的计划重排。

### 3.2 本次不扩展的执行能力

不增加工作流循环、并行、等待、子工作流、无约束脚本环境、Webhook 工作流触发、自动重试、取消运行或从失败步骤续跑。JavaScript 代码节点仅处理显式输入的本地计算，不能访问网络、文件、环境变量或调用命令。开始节点可表达手动、固定间隔、Cron，沿用已有后端。独立条件节点属于本次交付，多个 ELSE IF 集中在同一个节点中，不再增加 Switch 节点。

不增加 LLM 节点或 LLM 生成工作流功能。“AI 开发”在此指使用 AI 辅助实施与维护，不改变确定性 API 编排业务。

六类节点中 API、数据处理、代码、条件判断合计最多 20 步，开始/结束为唯一虚拟节点。筛选等操作集中在一个数据处理节点，不按操作拆节点类型；公共后续节点支持汇合，不增设合并节点。旧 API runIf 无损兼容，新流程以独立条件节点为主。草稿与部署版本分离、持久化未保存编辑和自动保存业务配置均不在本次范围；其中版本分离需要独立设计部署定义的存储及触发读取路径。

v2 部署/发现/触发及定时入队要求图中至少一个 API 节点，保持 API 调用编排定位；不要求每条条件路径都实际调用 API。没有 API 的草稿和单节点代码样本允许使用，不能作为公共纯计算工作流部署。节点数量仍为六类。

流程变量配置放在已有节点内，不增加赋值节点。赋值面板支持固定值、字段引用、对象组装、标量文本拼接和处理/代码结果；公式、日期计算、显式类型转换、自增/数组追加由代码计算完整新值，再统一 assign，不把表达式塞进来源模板。不同加工用条件分支连接数据处理或代码节点。

列表按键关联、分组求和及简单数学/日期计算可由 JavaScript 在输入数据和资源预算内完成。不隐式逐条调用 API、不自动翻页拉全量；场景 15 的单条接口循环调用仍不在覆盖范围，不能通过代码节点或 UI 暗中补外部调用循环。

运行按钮执行真实 API，可能有业务写入；文案使用“运行”，不能把真实运行包装为无副作用的“模拟测试”。

## 4. 页面与视觉设计

### 4.1 路由

| 路由 | 功能 |
| --- | --- |
| `/workflows` | 工作流列表，保留当前管理入口 |
| `/workflows/new` | 新建草稿，保存后 replace 到实体路由 |
| `/workflows/:id` | 编辑页，包含配置画布和该工作流运行历史 |
| `/workflows/:id/runs/:runId` | 只读运行画布，使用运行快照 |

运行详情必须核对 run.workflowId 与路由 id 一致。工作流软删除后，保留期内的历史详情仍可从运行记录入口访问；读取历史不能依赖“当前工作流未删除”。Shell 应正确识别子路由的标题和导航选中状态。

### 4.2 页面布局

2026-10-03 交互优化实施补充：编辑路由采用紧凑留白，顶部名称/状态/主操作加一条短工具栏，画布按可用高度伸展。属性默认关闭，展开宽约 360 px，并提供独立滚动与关闭按钮；点击节点只选中，双击或配置按钮打开，点击空白/Escape 关闭，未应用缓冲保留。专注模式覆盖导航和全局页头，退出恢复普通页面。

节点与条件出口提供本地添加入口；连线“＋”一次性插入并可一次撤销，保留后续其他依赖与祖先引用。插入时仅移动目标与后续路径，为新节点腾出横向空间，结束移到全部节点右侧。普通节点允许插在分支末端与公共汇合点之间，汇合的 scope 不改变；插入条件须明确选择后续出口，并拒绝把共享路径隐式移入某一分支。复制避开已有位置，删除前列出引用并要求先修正，删除无引用的节点时将后续接回其前置步骤。开始/结束仍为虚拟节点。

工具条保留添加、按需配置、撤销/重做、可搜索定位和专注模式；低频布局/JSON/能力刷新归入“更多”，业务保存项保留停止新触发的说明。合并适应画布控件，小地图按需开启。搜索遵循稳定依赖次序，普通选择不自动改变视角；显式定位只应用一次，先等待属性展开后的尺寸更新。Esc 只关闭当前最上层面板。手机默认展示步骤列表并在每行提供就近添加，图模式保持只读。

API 选择支持按名称/系统/标识搜索、按系统分组，保留失效或不可执行项及说明。参数映射优先表单，JSON、失败策略、依赖和节点管理放在可展开区域。节点类型被开关禁用时保留展示并说明原因；业务/布局未保存、待部署、执行受限分别显示，提示不增加顶部高度。Ctrl/⌘ Z、Shift Z/Y 和 S 支持编辑历史与保存；输入控件保留自身撤销，同一输入的连续编辑合并为一个历史事务。


```text
┌──────────────────────────────────────────────────────────────────────────┐
│ ← 工作流  名称  草稿/已部署  未保存        次操作  [当前主操作]  ⋯       │
├──────────────────────────────────────────────────────────────────────────┤
│ 配置 / 运行历史                         添加节点  自动布局  适应画布     │
├───────────────────────────────────────────────┬──────────────────────────┤
│                                               │ 节点名称                 │
│ [开始] → [查询客户] → [创建订单] → [结束]      │ API 与执行账号           │
│                                               │ 输入参数                 │
│ 可拖动画布、依赖连线、点击 + 添加              │ 条件分支 / 失败处理      │
│                                               │ 高级 JSON                │
├───────────────────────────────────────────────┴──────────────────────────┤
│ 校验问题，或本次运行状态 / 步骤列表 / 最终结果                            │
└──────────────────────────────────────────────────────────────────────────┘
```

点击“添加节点”只展示 API、数据处理、代码、条件判断四个可添加项；选择 API 后进入可搜索面板，开始/结束自动存在。避免常驻节点库挤压画布，点击添加为主，拖拽为补充。各节点卡片和侧栏示意见[节点 UI 规格](workflow-node-design.md)。

### 4.3 美观的具体要求

- 复用现有 CSS 变量、字体、按钮高度、圆角、边框和 Lucide 图标；不复制 Next.js 模板的应用壳层。
- API 节点初始宽度约 260 px，高度约 112–144 px，侧栏约 360 px；这属于实施起点，须通过实际页面调整。
- 节点展示系统图标、API 名称、HTTP 方法与路径摘要、账号摘要和状态。详细参数不铺在画布上。
- 白/深色画布保持低对比网格，选中边框与键盘焦点清晰，错误通过文字与图标同时表达。
- 依赖线使用统一箭头；只对实际 running 步骤对应的连接使用轻量动画。尊重 prefers-reduced-motion。
- 标题与路径截断，完整信息可在侧栏和可访问提示中查看；禁止长名称撑宽页面。
- 加载、失败、空列表、缺少可执行 API、目标失效都有明确状态，不显示无提示空白画布。
- 不把开发术语、框架版本或“DAG 编译成功”等内容放入普通操作提示。

### 4.4 新建及常见操作

1. 新建页默认仅有开始与结束节点，不生成占位可执行步骤；空图允许保存草稿，部署仍要求实际执行步骤及非空最终输出。
2. 填写名称，系统建议一个合法唯一标识，冲突时可修改；标识位于高级设置。
3. 点击添加节点，选择 API/数据处理/代码/条件判断；创建稳定 ID 并打开对应侧栏。
4. 新增节点默认接到当前选中的普通步骤后面；选中条件节点时必须选择具体出口。没有选中时只在唯一末端后串联，多个末端时明确选择，不擅自合流。
5. 从开始节点添加的根步骤没有 dependsOn 和分支 scope；多个根节点仍串行执行。
6. 配置集成和账号，填写或选择参数来源。
7. 保存草稿；配置缺失显示在节点上，阻止部署但不阻止合法草稿保存。已有部署保存业务修改前，明确说明停止新的触发，重新部署后恢复；已经接受的运行继续。
8. 部署完成后提供运行入口；运行输入默认展开为当前默认输入，使用与开始节点相同的字段表单并保留高级 JSON，明确本次输入替换默认输入，不自动深度合并。

不自动选择列表中的第一个账号。只有一个有效候选时可以展示推荐并由用户明确确认绑定。无认证 API 显示“无需账号”，不要求创建空账号。

### 4.5 连线、复制、删除与顺序

- 普通步骤 A → B 表示 B.dependsOn 包含 A.id；从条件出口添加步骤还必须写入分支 scope，不能只增加 dependsOn 就宣称支持分支。
- 开始连线是无依赖节点的展示；删除该线不能制造“节点不被执行”的假象，开始连线由根节点自动派生。
- 结束线由 output 引用和终端节点派生，以样式/标签区分“结果来源/流程结束”；最终映射始终在整个流程完成后计算，不因单个分支到达结束而抢先返回。
- API、数据处理、代码和条件判断均可作为“在此汇合”的目标，原子设置前置步骤和公共父 scope，支持空分支直接继续；汇合到新条件后只判断一次，再建立新出口作用域。结束卡片提供“在结束汇合”，依原 scope/末端派生连线，不保存第二份执行边或中断其他路径；已有后续不能被此操作静默删除。详见[汇合执行规则](workflow-node-design.md#execution)。
- 阻止自连接、重复连接、环、结束出线、指向开始及跨互斥分支绕行；服务端再次校验。结束输出来源在侧栏修改，不拖线改映射。
- 添加依赖不会自动映射参数。字段选择器只提供依赖闭包内的上游步骤，缺少依赖时先明确提示添加依赖。
- 删除/断开先列出 input、source、runIf、branches、scope、变量读写、按分支来源及 output 的影响；删除写入者可能使后续改读初始值，必须明确提示。调整一次应用并可撤销。
- 删除中间节点不自动把前后节点连接；这种重写可能改变依赖语义。
- 复制生成新 ID，保留类型配置、有效 API 绑定及合法上游引用，不复制下游连线。复制条件时生成新的本地分支 ID，不复制整个分支子图；复制后不自动运行。
- 修改显示名称只改 title，不改变 id。高级修改 id 必须用结构化路径修改所有引用和依赖，禁止全局字符串替换。
- 节点坐标不决定执行次序。保留 steps 声明次序，自动布局不重排 steps；侧栏提供步骤优先次序调整，用于无依赖步骤的稳定执行顺序。
- 撤销重做只作用于未保存的定义与布局，最多保留 50 次用户操作；拖动在结束时形成一次操作，不把每帧或运行轮询写入历史。

### 4.6 画布的操作分区与默认行为

画布有五个明确分区：顶部业务操作、画布工具条、节点与连线、右侧检查器、底部信息面板。业务操作与画布操作不能混在一个菜单中。

| 分区 | 常驻内容 | 按需出现的内容 |
| --- | --- | --- |
| 顶部 | 返回、名称、部署状态、当前主操作及必要的次操作 | 保存中、版本冲突、当前版本、暂停 |
| 工具条 | 添加节点、撤销/重做、自动布局、查看全图、步骤列表 | 缩略图开关 |
| 画布 | 六类节点、依赖及带标签的分支连线 | 节点添加按钮、选中节点操作、汇合入口 |
| 右侧 | 选中节点的配置或运行详情 | API 更换、字段选择、账号修复 |
| 底部 | 校验数量或当前运行摘要 | 问题列表、步骤列表、最终结果 |

默认不常驻 MiniMap，不放不必要的全屏、图片导出和白板工具。超过约 8 个执行步骤或流程超出可见区域时可提供缩略图开关，但不能遮挡底部操作。

顶部只突出一个主按钮：新建或未部署且有修改时为“保存草稿”，已保存待部署时为“部署”，已部署且无业务修改时为“运行”。已部署且有业务修改时主操作为“保存并部署”，将“仅保存草稿”作为次操作并说明停止新触发的影响。布局保存使用次操作，业务状态不因此降级；完整可用条件见第 4.10 节。

画布交互规则：

- 点击节点选中并打开侧栏，不需要双击；再次点击同一节点不清空已输入字段。
- 点击空白取消节点选择，未应用的 JSON 编辑先提示，不丢弃内容。Escape 先关闭临时选择面板，再关闭侧栏。
- 节点拖动只从标题/专用拖动区开始；按钮、文本选中和侧栏滚动不触发节点移动。
- 鼠标滚轮/触控板默认平移画布，工具条 +/− 调整缩放，双指缩放支持触控设备；明确配置 React Flow 的滚动行为，不让画布吞掉整个页面的正常滚动。
- Space + 拖动平移，拖动画布背景也可平移；输入控件获得焦点时 Space 仍输入空格。
- 区分“查看全图”和“定位节点”：全图模式按完整边界计算缩放，不能用固定 0.4 下限使 20 步横向流程无法完整显示；定位节点恢复约 0.8–1.0 的可读比例。普通编辑缩放初始上限 1.5，实际取值由阶段零验证，React Flow 与 fitView 的缩放边界须一致。
- 适应画布保留约 15% 内边距，计算可用区域时扣除侧栏、工具条和展开的底部面板；侧栏开关后仅在选中节点被遮挡时局部平移，不反复重设用户视口。
- 节点动作不依赖悬停才能发现：选中节点显示 + 和更多菜单，键盘聚焦也可操作；触控设备显示可点击按钮。
- 侧栏参数即时更新本地定义，显式“保存”写入服务器；关闭侧栏不是撤销配置。
- 桌面也可打开步骤列表，按引擎稳定拓扑次序显示、搜索并定位步骤；开始和结束单独列在首尾。步骤列表与画布共享同一选中状态，不新增一套配置模型。
- 选中字段引用时高亮来源节点和相关依赖路径，取消选择后恢复简洁连线；运行页提供“定位执行中步骤”。用户主动平移或查看其他节点后不自动抢回视口，轮询不触发全图重排。

### 4.7 六类节点的具体内容

API 节点示意：

```text
┌──────────────────────────────┐
│ [系统图标] 查询客户       ⋯  │
│ GET  /customers/{customerId} │
│ CRM · 生产环境 · 服务账号    │
│ 2 个参数已配置              │
│                待配置 / 成功 │
└──────────────────────────────┘
              [+]
```

| 节点 | 展示 | 点击后的侧栏 | 可操作项 |
| --- | --- | --- | --- |
| 开始 | 输入/变量数量、手动或定时摘要 | 输入声明、默认输入、流程变量、触发配置 | 添加根步骤；唯一，不可复制删除 |
| API | 标题、方法/路径、集成/账号、配置与赋值摘要 | API、目标、参数、失败策略、更新变量、预览 | 添加后续、复制、删除、更换 API |
| 数据处理 | 来源、操作摘要、更新变量数 | 来源、操作列表、更新变量、样本预览 | 编辑/排序操作；添加后续、复制、删除 |
| 代码 | JavaScript、输入/输出/更新变量数 | 输入来源、代码编辑、返回 Schema、更新变量、样本执行 | 展开编辑、行列诊断；添加后续、复制、删除 |
| 条件判断 | IF/ELSE IF/ELSE 行及出口标签 | 条件顺序、各出口赋值、命中预览 | 增删/重排 ELSE IF、各出口添加后续、汇合 |
| 结束 | 输出字段数量、配置状态 | 返回字段、按分支来源、可选引用 | 编辑映射；唯一，不可复制删除或添加后续 |

开始/API/数据处理/条件/结束见[节点专项设计第 3–7 节](workflow-node-design.md#node-start)，代码见[节点第 12 节](workflow-node-design.md#node-code)及[详细代码 UI](workflow-code-node-development-plan.md#ui)。条件卡片高度随分支数增加，端口与分支行对齐；折叠不得导致出口身份错位。

API 的 display title 与实际 API name 分开：title 默认取 API 名称，用户可以改成“查询客户”之类业务名称；更换 API 时不覆盖用户改过的 title。标题默认值是否被用户修改由当前编辑态判断，不为此新增数据库字段。

配置态与运行态共用节点骨架，但两种状态不混写：配置态显示“待绑定/缺参数/已配置”，运行态显示“等待/执行中/成功”等。用户即使配置了全部字段，也不能看到表示真实执行成功的绿色成功图标。

无依赖执行步骤自动显示开始线；结果引用线默认用虚线并标记“结果来源”。终端步骤及无后续的条件出口可显示“结束后生成结果”线。没有步骤时显示开始到结束的占位提示，不生成可执行步骤。

### 4.8 添加面板、快速串联与插入

添加菜单固定为 API、数据处理、代码、条件判断；API 子面板展示搜索框与系统筛选，候选展示名称、系统、方法/路径和状态。不展示 LLM/循环等不在范围的节点，代码仅显示 JavaScript。

| 入口 | 创建方式 | 依赖变更 |
| --- | --- | --- |
| 顶部“添加节点” | 选择四种执行节点之一 | 按第 4.4 节处理；多末端或条件出口明确选择 |
| 普通节点/条件出口 + | 添加对应路径的后续步骤 | 新增 dependsOn 并继承/追加 scope，原下游不变 |
| 依赖线上的 + | 在这一条依赖之间插入 | A→B 改 A→N→B；B 其他依赖不变 |
| API 页面“用于工作流” | 新建流程或选择现有草稿 | 只预选 API，账号仍按目标规则明确绑定 |

插入操作是一次可撤销的原子编辑，不能先断旧线再等待配置。取消添加不改变原图。普通步骤 A→N→B 保留 B 对 A 的传递引用与正确 scope；插入条件节点必须明确 B 接在哪个出口，检查受影响子路径，不默认把 B 同时接到所有出口。间距不足仅移动必要节点，或提供显式自动布局。

搜索请求采用现有分页，query/system 改变时清除旧游标，约 250 ms 防抖；相同 API 共享详情与目标候选缓存。最多 20 个执行步骤（API/数据处理/代码/条件合计），上限后禁用添加/复制并说明，条件内添加 ELSE IF 按独立分支上限处理。

第一版不实现从端口拖到空白后自动弹窗、复杂套索及整片子图复制；点击 + 与键盘操作已覆盖主流程。

### 4.9 侧栏的信息层级与连续操作

API 侧栏使用“配置 / 请求预览”两页；配置页依次为：

1. 步骤名称，API 摘要和“查看定义 / 更换 API”。
2. 执行目标：集成，API 基础地址摘要，账号与有效性。
3. 输入参数：必填优先，参数来源与值；可选字段可折叠。
4. 更新流程变量：目标变量 / 新值来源，默认折叠；简单直接引用不要求配置变量。
5. 执行规则：前置步骤、所属分支只读摘要、失败处理，默认折叠。
6. 高级：步骤标识、整体 input JSON；旧 API 的 runIf 以“历史执行条件”保留。新流程通过条件节点配置分支。

侧栏顶部固定步骤名称与关闭按钮，底部固定“上一步 / 下一步”和当前配置提示；长参数区内部滚动。上一步/下一步按步骤列表的稳定拓扑次序选择执行步骤，不依赖节点坐标；从节点或条件出口 + 添加后续按对应路径处理。配置即时更新节点状态；错误在提交或字段失焦后展示，不在刚输入一个字符时闪出红色错误。

字段行的具体交互：

```text
customerId *  [Body]  string
[ 上游结果 ▾ ]  [ 查询客户 → id ▾ ]
                                更改来源 / 清除

amount *      [Body]  number
[ 开始输入 ▾ ]  [ amount ▾ ]

currency      [Body]  string
[ API 默认值：CNY ]             设为固定值
```

来源改变时不立刻清空已配置值：先保留原值作为编辑缓冲，选择新的固定值/字段后原子应用。切换到“未设置/API 默认值”会从 input 移除该 key，属于显式用户动作。字段选择面板显示节点名、字段路径、类型和必需依赖；不自动按同名字段连线或映射。

已选引用以“查询客户 → 客户编号”的字段标签呈现；缺少业务名称时显示准确路径。标签可查看路径及类型并定位来源。节点同名时附带稳定 ID 消歧；普通引用保存模板路径，按分支来源保存条件 ID、稳定分支 ID 与各来源映射，不保存显示文案作为标识。

其他节点的简化表单：

- 开始使用“字段名 / 类型 / 必填 / 允许空值 / 说明”声明输入，保存为 graph.inputSchema，服务端所有触发入口共用校验；nullable 字段保存为基础类型＋null 的 type 数组，规则见节点专项。整个默认值对象仍保存在 workflow.input，不做深度合并。未声明 Schema 的老流程保持兼容。
- 开始增加“流程变量”页，使用“名称 / 类型 / 允许 null / 初始来源 / 说明”；输入字段可一键“作为流程变量使用”，生成 initial 引用，不复制默认值。原有参数来源不自动由 trigger 换成 vars。
- 结束使用“输出字段名 / 来源 / 引用字段或固定值 / 允许缺失”，支持按分支选择来源。重复字段名阻止应用，删除可撤销。
- 改名/删除开始字段先列出引用它的 API、条件和输出；用户可以同步迁移这些结构化引用，也可以保留作为“仅运行时提供”的字段。默认输入没有 key 不等于引用节点已经不存在。
- 数据处理使用“数据来源 + 有序操作列表 + 样本预览”，常用预设生成同一组 select/filter/sort/slice/count 操作；重排后立即更新类型检查与预览状态。
- 代码使用命名输入/返回表，支持允许空值、input 字段插入/补全和三个固定模板；默认只填写命名输入样本验证计算，展开上游映射验证后才填写祖先样本。代码根字段仍全部必填，允许 null 不等于允许缺失，不隐式转换或自动兜底。
- 条件判断使用有序 IF/ELSE IF 列表及固定最后的 ELSE；每个分支内为“全部满足/任一满足 + 添加条件”。exists/not_exists 隐藏比较值，分支可重排并保留稳定 ID，预览明确首次命中及后续未判断。
- API/数据处理/代码提供共用“更新流程变量”，条件各出口提供“命中后更新变量”；来源包括当前成功结果、开始输入、只读运行信息、进入节点时的变量及合法上游。常见操作在数据处理配置，多来源运算在代码编辑器，赋值面板不重复建设处理器。
- 运行输入复用开始字段控件和 JSON 缓冲，修改只作用于本次运行。显式声明的 Schema 才约束服务端；样本或引用推断只是提示。复杂结构保留 JSON 入口，未提供默认值的必需字段可在手动运行时补齐。

配置与预览切换保留局部编辑内容；失效不清空参数。运行侧栏按类型展示概览、输入/结果摘要和变量变更；读取、写入来源及前后值限长脱敏，区分已提交/未提交，不假装可修改历史。

### 4.10 校验与主要按钮的状态

| 场景 | 保存 | 部署 | 运行 | 用户提示 |
| --- | --- | --- | --- | --- |
| 空的新建流程 | 名称/key 合法即可保存 | 禁用 | 禁用 | 添加 API 并配置最终结果 |
| API 已选择但未绑定 | 保存草稿 | 禁用并定位 | 禁用 | 具体节点需要集成/账号 |
| JSON 仍有语法错误或未应用 | 阻止对应保存 | 阻止 | 阻止 | JSON 区域保留原文本并定位错误 |
| 已部署、无修改 | 无修改时禁用 | 已部署状态 | 可运行 | 显示正在使用的版本 |
| 已部署、仅坐标改变 | 保存布局 | 保持已部署 | 先保存布局再运行 | 位置未保存，不是配置失效 |
| 已部署、参数或绑定改变 | 仅保存草稿，并明确停止新触发 | 主操作“保存并部署” | 明确的“保存并部署后运行”，顺序执行 | 每步失败都停在该步，显示已完成阶段和调度状态 |
| 账号失效 | 可保存草稿 | 阻止 | 阻止 | 到认证中心修复并刷新 |
| 已部署、所需 v2/代码能力关闭 | 按开关约定保留编辑/只读能力 | 阻止新部署 | 阻止新触发 | 已部署 · 平台暂未开放执行；在途任务仍显示真实进度 |
| 版本冲突 | 保留编辑和缓冲 | 阻止继续 | 阻止继续 | 查看服务器版本；复制本地配置或明确放弃后加载 |

结构错误（环、非法/重复 ID、错误条件语法、失效分支 ID、非法 scope、越界引用及确定无效的操作链）属于不可保存定义；缺少执行绑定、输入值和最终结果属于待部署问题。前端只提示可确定问题，服务端同步扩展类型、分支及来源校验，不能沿用“所有步骤必须有 action”的旧规则处理本地节点。

定时部署先检查默认输入满足显式 inputSchema，再检查无分支约束且没有旧 runIf 的步骤中必需 trigger 引用。条件保护下的引用按实际路径分析，不能要求所有互斥路径的字段都同时存在；无法静态判定时提示风险，不执行上游 API 求值。仅手动触发允许本次补输入。新增校验列入阶段一；样本预览成功不等于所有输入都可执行。

问题列表格式固定为“步骤 / 字段 / 问题 / 修复动作”，例如“创建订单 / customerId / 引用的步骤不是前置步骤 / 添加依赖”。参数引用选择只展示上游；高级 JSON 引用了未连接的节点时，提供“添加依赖并保留引用”，进行环检查后原子更新，不能后台默默加线。

本次不自动保存业务定义。已部署流程有业务修改时，在保存操作附近持续显示“保存草稿后停止新的触发，重新部署后恢复；已接受的运行继续”。“保存并部署”是两个有版本检查的请求，不能承诺原子切换或不中断调度：保存成功而部署失败时显示“已保存，但部署失败；新的触发已停止”，保留错误定位和继续部署入口。再次操作从已保存的新版本继续，不能重新提交已完成的阶段。

前端本地校验、服务端错误和问题列表采用第 8.3 节的诊断约定。错误能够定位到具体节点和控件；未结构化的旧错误保留在页面级提示，不解析报错文本猜测位置。

### 4.11 一个完整的用户操作案例

目标：输入客户编号，查询客户，再创建订单，最后返回订单 ID。

1. 在开始节点填写默认输入 `{ "customerId": "C-100", "amount": 100 }`。
2. 添加 CRM 的查询客户 API；选择生产集成和已验证账号。
3. 参数 customerId 的来源选择“开始输入 → customerId”，保存为 `{{trigger.customerId}}`。
4. 从查询客户节点 + 添加创建订单 API，自动生成依赖。
5. 创建订单 customerId 选择“查询客户 → id”；amount 选择“开始输入 → amount”。
6. 点击结束节点，新增 orderId，选择“创建订单 → id”。
7. 打开请求预览；查询客户可用开始输入解析，创建订单需要填写查询客户样本响应 `{ "id": "C-100" }`，不自动执行查询客户。
8. 保存草稿并部署，显示返回的新版本；运行时显示明确的本次输入。
9. 查询客户完成后创建订单进入执行中；点击节点查看脱敏输入与响应摘要，结束节点显示最终 orderId。
10. 从历史打开本次运行。之后修改当前配置不会改变历史节点、依赖、输入来源和 API 版本记录。

这个主流程不要求用户输入模板字符串、不要求理解 DAG，也不要求在 API 页面、集成页面和账号页面之间反复跳转。

### 4.12 定时配置与计划时间预览

开始节点保留手动、已有四种固定间隔和 Cron。常用 Cron 提供“每天指定时间”“每周指定日期和时间”等表单入口，生成现有五字段表达式；自定义表达式仍可直接编辑，无法映射到常用选项时保留原表达式，不强行改写。

- 时区使用明确的 IANA 名称，已有流程保留当前时区；新建默认值明确显示，不仅写“本地时间”。摘要同时显示规则与时区，例如“每天 09:00 · Asia/Singapore”。
- 显示未来三次计划触发时间，复用服务端 cronx 解析和现有固定间隔规则。新增只读计算用途的 `POST /api/workflows/preview-schedule`，不创建或保存工作流、不入队，接口见第 8.1 节。
- 修改表达式、间隔或时区后使旧预览失效，只显示最新请求对应的结果；语法错误定位到触发设置，合法但没有可计算的未来时间给出独立说明。
- 预览是按服务端当前时间计算的计划，不是准时执行保证；部署后以返回的 nextRunAt 更新显示。排队或容量限制可能延迟执行，停机错过的计划不自动补跑；Cron 的夏令时处理沿用现有实现。
- 能力开关关闭时，部署状态保留，计划时间标明“规则计划，当前不会触发”；后台推进禁用到期项但不入队，不能阻塞其他流程。恢复前对受影响的已部署计划做统一重排，过期项从未来时间继续；恢复步骤和失败处理见[调度开关契约](workflow-code-node-development-plan.md#schedule-gates)。计划预览本身仍可计算，不代表当前允许执行。
- “查询当天订单”等参数可选择运行信息中的 businessDate。它按本次计划时间及工作流时区计算，与画布查看时间或 worker 领取时间无关；非定时调用按本次触发时间计算，见[运行信息](workflow-node-design.md#run-metadata)。

## 5. 参数、条件与输出配置

### 5.1 API 与绑定

使用 `GET /api/actions` 搜索和分页，节点需要详情时使用 `GET /api/actions/{id}`。保存 action 优先使用 API UUID，避免跨系统同名 actionKey 歧义；加载兼容 UUID、系统限定 key 和历史唯一 key。

该决定需要配套修改 `runtimeWorkflowSummaries` 与 `workflowPolicyCheck`：按 UUID/系统限定 key/唯一历史 key 解析到同一个 ActionDefinition，然后用 action.ActionKey 调用现有 policy.AllowsAction，和后台逐步骤 AuthorizeStep 一致。歧义 key、失效 API 或解析失败均拒绝；不能“UUID 匹配或 key 匹配任意一个通过就授权”，不能扩宽 token 的 allowedActions 规则。可批量建立查询映射，遇到重复裸 key 时标为歧义，不按数组顺序取第一个。补 UUID、限定 key、deny 优先和跨系统同名用例；未完成这个适配前不能把前端保存格式改为 UUID。

目标候选直接使用 `GET /api/actions/{id}/execution-options`。按 integration.id 和 account.id 关联，不按显示名称匹配。根据 requiresAccount 区分认证要求。

账号可执行条件与现有规则一致：enabled、active、lastVerifiedAt 存在、verifiedRevision 匹配 revision、verifiedTargetVersion 匹配目标版本。无效的原绑定保留显示及修复入口，不能静默切换账号。更换 API/集成时清理不再属于该目标的绑定；输入参数先展示不兼容项再由用户确认处理，不能静默丢失。

### 5.2 参数来源

| 来源 | 界面 | 写入 input |
| --- | --- | --- |
| 固定值 | 类型对应的输入控件 | 原始 JSON 值 |
| 触发输入 | 选择字段或输入路径 | `{{trigger.customerId}}` |
| 运行信息 | 选择触发时间、计划时间、时区或业务日期 | v2 `{"$value":{"kind":"run","field":"businessDate"}}`；字段只读且固定到快照 |
| 流程变量 | 选择变量，展示类型及可能的上游写入者 | `{{vars.orderId}}`；读当前节点进入时的版本 |
| 上游输出 | 选择上游节点和字段 | `{{get_customer.data.id}}` |
| 按分支选择 | 选择条件，再为可能命中的各分支配置来源 | v2 `$value.kind=branch`；只解析命中来源，契约见[共用数据契约](workflow-node-design.md#shared-contract) |
| 组合文本 | 高级模板输入 | `客户：{{get_customer.name}}` |

上例 data.id 仅在真实输出具有 data 时使用。API 没有包装层时应选择 get_customer.id，不按 UI 偏好强行包一层。

参数表根据 inputSchema 的 properties/required/type 渲染，requestConfig.parameters 补充参数位置、名称和说明；运行输入仍是 API 已支持的顶层参数对象。复杂对象、数组和暂不支持的 Schema 使用字段级 JSON 或整体 JSON，不建设通用 JSON Schema 表单平台。

支持 string、number、integer、boolean、null、object、array 的正确值类型；空字符串、未设置和 null 分开处理。数值控件检查安全整数，超过 JavaScript 安全整数范围时不允许静默四舍五入；提示按照 API 的字符串契约传值，或扩展无损 JSON 处理后再开放该数值编辑能力。

这里的 null 是 JSON 编辑与旧 Schema 的保留能力，不代表当前 requestConfig v1 参数允许 null。v1 的参数类型检查只支持 string/number/integer/boolean/object/array，显式 null 会被拒绝；控件必须按实际 API 契约决定是否允许 null，不能把“留空”统一写成 null。

已有嵌套或混合模板进入高级模式时必须无损保留。整体 JSON 有独立编辑缓冲区，校验成功点击应用后才替换定义；切回表单不能删除未知字段。不同编辑模式共享同一份已应用的 input。

### 5.3 字段选择器

- 来源包括 trigger、运行信息、已声明 vars、当前路径可用上游输出，以及条件所需 status。互斥输出通过“按分支选择”；变量读写须由依赖明确先后，不能仅因名称存在就认为时序有效。运行信息显示“本次固定值”，与原始输入和当前变量分别展示；不生成 `{{run.*}}` 引用或占用步骤 ID。
- assign 专属来源区允许当前节点成功输出；input/source/条件仍禁止自引用。组合文本支持固定文本与标量字段标签，不要求普通用户手写模板。
- 优先使用 API 输出 Schema，其次用户提供的响应样本并标明“样本推断”；均无时可填手工路径并标记类型未知。数据处理按操作推导 result 类型，不能自动调用上游获取字段。
- 测试运行摘要只作为参考，不能据单次结果推断稳定 Schema；脱敏值不能自动填成业务值。
- 支持整个响应、数组索引及特殊字段名路径，严格对齐 `internal/jsonutil/path.go`，例如 `get_customer.items[0].id`、`get_customer["key.with.dots"]`。
- 禁止由选择器生成后端不支持的 JSONPath、过滤表达式、函数或 JavaScript。
- Schema 变化只影响建议列表，不自动替换已配置引用。类型已知且明确不匹配时阻止部署；无法静态判断时提示并由运行时验证。
- 默认触发输入没有某字段不等于该字段永远无效；允许本次运行提供，提示默认定时输入可能缺失，不能错误地禁止所有手动运行场景。

### 5.4 条件分支与失败处理

新流程使用独立条件节点，按顺序配置 IF、多个 ELSE IF 和唯一最后的 ELSE。首次匹配后停止判断，其余出口不激活；判断错误不是 false，不自动走 ELSE。每个条件组使用现有叶子操作符与 all/any 限制；右侧支持变量是 v2 新增能力。完整配置与 UI 见[条件节点](workflow-node-design.md#node-condition)。

已有 API runIf 在高级区无损编辑，其 skipped 继续保持旧的单步语义，不转换成整条分支关闭。新条件节点用 scope 控制整个路径，再由普通后续节点汇合。不能只把 runIf 表单移动到画布就称完成条件节点。

条件比较对象为 trigger、上游结果或 status。exists 判断字段存在，null 仍算存在；缺失字段的其他比较会报错。可能跳过的上游结果应先用 exists 或 status 条件保护。

all/any 按配置顺序短路求值，顺序属于执行语义。编辑器保留原顺序，提供上移/下移，不按字段名自动排序。例如 all 中先判断 `exists(get_customer.id)`，再比较该字段；反过来在字段缺失时会先报错。界面提供“字段存在后再比较”的组合填写方式，用户应用后生成有序 all 条件，不引入新运算符，也不静默改写已有条件。

预览与运行都先检查 scope，再兼容旧 runIf，最后解析激活节点的 input。分支未选中或旧条件不匹配时显示跳过原因，不要求构造其输入；具体预览约定见第 5.9 节。条件节点还须区分“未命中”和短路后“未判断”。

API 失败处理只显示“停止流程”和“继续后续步骤”；失败不赋值，继续后可能保留旧变量，可用条件检查 status 选择兜底。unknown 始终停止。处理、条件求值和变量赋值错误直接停止；API 调用成功而赋值失败分别展示两项事实，不能被 onError=continue 吞掉或自动重试。

现有认证请求编辑器的 ConditionEditor 与工作流条件语法不同，不能未经核对就复用其数据协议。可以复用基础表单控件。

### 5.5 最终结果

结束字段可取固定值、trigger、运行信息、步骤输出、vars 最终值或按分支来源，不自动返回全部变量。按分支只解析命中路径；允许缺失仅对最终整值引用生成 `{{?path}}` 并返回 null，步骤 input 和 assign 不以缺失静默兜底。

示例：

```json
{
  "customerId": "{{get_customer.id}}",
  "orderId": "{{create_order.id}}",
  "notice": "{{?send_notice.message}}"
}
```

部署前 output 必须为非空对象；列表/计数放在命名字段内。结束为虚拟节点，不占用 20 步限额，在所有有效步骤完成后映射一次，不是提前终止流程的 return。

### 5.6 API 定义、工作流配置与请求的职责边界

工作流选择一个已有 API，再配置这次调用的数据和执行账号。HTTP 方法、相对路径、参数位置、静态业务头、bodyFormat、响应判断和超时继续由 API 定义管理。

| 数据 | 在哪里修改 | 画布中的表现 |
| --- | --- | --- |
| API 方法/路径、参数声明 | 现有 API 定义页 | 只读摘要与查看定义入口 |
| 业务成功条件、响应 Schema | API 定义页 | 只读响应规则摘要 |
| API 基础地址、环境、认证实例 | 集成/认证中心 | 选择集成，展示只读地址及环境 |
| 凭据、OAuth 授权、账号验证 | 认证中心 | 选择账号、显示有效性、修复入口 |
| 本次参数来源、条件、失败策略 | 工作流节点侧栏 | 可编辑 |
| 本次输入及步骤结果 | 运行输入/运行详情 | 输入可填写，历史只读 |

不在每个 API 节点增加 URL、认证头、请求体格式等覆盖字段，不复制一份 API 定义到工作流。用户需要不同路径或响应规则时编辑/创建 API；需要不同地址时选择集成。

### 5.8 参数默认值、示例与请求位置

现有 `executor.PrepareInput` 会对缺失参数应用 requestConfig.parameters 的 default，检查类型并拒绝 v1 未声明参数；`Catalog.ValidateInput` 对准备后的有效值做 Schema 校验。前端提示应与此一致。

| 情况 | 编辑体验 | 保存到 input |
| --- | --- | --- |
| 参数未配置，但 API 有 default | 显示“使用 API 默认值”和默认值摘要 | 省略该 key，不固化为显式值 |
| 用户点击“设为固定值” | 可编辑原默认值 | 显式写入 key，后续 API 默认值变化不覆盖它 |
| 参数只有 example | 展示建议与“使用示例”按钮 | 未点击前不写入、不假装已经配置 |
| required 且有合法 default | 默认值可满足参数需求 | 省略 key，服务端使用 default |
| optional 且没有值 | 显示“未设置” | 省略 key |
| 用户输入 0、false 或空字符串 | 保持真实值并按 API Schema 校验 | 不能按真值判断而删 key |
| 参数改名/删除，旧 input 仍有 key | 保留值，提示“API 已不接受此参数” | 用户明确迁移或删除，不能静默扔掉 |

API 示例与默认值不是同一回事，不能像当前普通 API 测试表单那样直接把 exampleInput 当作每个新工作流节点的执行数据。

重要的扁平参数规则：`requestConfig.parameters[].name` 是 input 的准确 key；`in=body` 且 name 含点时，BuildRequest 才把它展开成嵌套 JSON 请求体。前端不能提前展开，否则会被判成未知参数。

例如 API 声明 `customer.id`、amount 两个 body 参数：

```json
{
  "input": {
    "customer.id": "{{get_customer.id}}",
    "amount": "{{trigger.amount}}"
  }
}
```

解析后有效 input 是 `{ "customer.id": "C-100", "amount": 100 }`，实际请求体由后端构建为 `{ "customer": { "id": "C-100" }, "amount": 100 }`。参数名的点与模板引用中的点承担不同含义，字段编辑器不能用同一种 split('.') 处理两者。

界面按 Path/Query/Header/Body 展示位置标签，不让用户拖参数改变位置。query 数组按当前 builder 生成重复 query key；form 只允许标量；header/path 不允许对象和数组；认证值必须来自账号。复杂输入不能通过高级 JSON 绕过这些规则。

对于 requestConfig schemaVersion=0 的旧 API，展示旧请求规则：GET/HEAD 的剩余参数进入 query，其余方法剩余参数进入 JSON body，路径参数先展开。该行为由现有 builder 决定，不能按 v1 渲染方式擅自改请求。

### 5.9 节点预览：复用实际处理逻辑

请求预览展示的是“按当前定义与样本输入构建的请求”，不发送业务 API，也不验证上游连通性或真实响应。单击“生成预览”触发，参数改变后标为过期；避免每次编辑都请求后端。

同一 preview-step 接口按节点类型处理：API 构建请求、数据处理执行纯数据操作、代码在受限 worker 中执行样本、条件判断返回首次命中出口与短路过程。本地节点没有 HTTP 请求/账号字段，不伪造 request 或 httpStatus。处理/条件复用 Go 函数，代码复用正式 CodeRunner；节点契约见[共用预览](workflow-node-design.md#shared-contract)与[代码样本执行](workflow-code-node-development-plan.md#preview)。

预览页包括：数据来源、有效输入、URL、业务请求头、请求体、API/集成版本及认证状态摘要。明确展示“真实认证在运行时注入”，不展示认证令牌。大内容使用现有 RequestPreview/safejson 的截断策略，不自己在浏览器构造请求。

#### 5.9.1 API 只有具体输入且没有分支或执行条件时

直接使用现有 `/api/actions/{id}/preview`，传 input、integrationId、connectionKey、expectedApiVersion、expectedIntegrationVersion 和 expectedAccountRevision。实例无需账号时省略 connectionKey。响应以服务端 request 为准，禁止前端重新组合 URL。

若 input 包含任何工作流占位符，即使 Schema 类型为 string，也不得调用普通 API 预览把 `{{trigger.id}}` 当成业务字符串。必须进入样本解析预览路径。

只要配置了 scope、runIf、vars 引用、assign、按分支来源或运行信息来源，或焦点为数据处理/代码/条件节点，就进入工作流步骤预览接口；不能绕过分支、变量或时间样本直接构造 API 请求。检测来源须识别 v2 ValueSource 标记，不能仅搜索字符串占位符，也不能把 kind=run 对象原样发给普通 API 预览。

#### 5.9.2 包含触发/上游引用或执行条件时

新增 `POST /api/workflows/preview-step`，支持尚未保存的工作流。handler 分派请求构建、纯函数处理与受限 CodeRunner，不建设通用执行模拟器或任意脚本 API。注册在管理端 workflows 路由内，允许 owner/admin/developer，拒绝 viewer 的 POST。

本节默认 previewMode=workflow，省略该字段时保留相同语义。代码专有 code_inputs 模式接收字面 sampleInput，只验证 main/返回/限额，不求值 scope、上游来源或 assign；响应 validationScope=code_only，省略 activationEvaluation，assignmentPreviewStatus=not_applicable，不标记整条流程预览成功。两种模式的样本字段互斥，均通过共享 CodeRunner，完整协议见[代码样本执行](workflow-code-node-development-plan.md#preview)。preview-step 不套 a.audited 的数据库事务包装。

以下请求展示仍需兼容的 v1 API 预览；v2 definition 使用[完整节点定义示例](workflow-node-design.md#execution)，外层样本字段不另建一套：

```json
{
  "definition": {
    "steps": [
      { "id": "get_customer", "action": "api-customer-uuid", "integrationId": "crm-target-uuid", "connectionKey": "crm-account-uuid", "input": { "customerId": "{{trigger.customerId}}" } },
      { "id": "create_order", "action": "api-order-uuid", "integrationId": "order-target-uuid", "connectionKey": "order-account-uuid", "dependsOn": ["get_customer"], "input": { "customer.id": "{{get_customer.id}}", "amount": "{{trigger.amount}}" } }
    ],
    "output": { "orderId": "{{create_order.id}}" }
  },
  "stepId": "create_order",
  "trigger": { "customerId": "C-100", "amount": 100 },
  "sampleOutputs": { "get_customer": { "id": "C-100" } },
  "sampleStatuses": { "get_customer": "success" },
  "expectedApiVersion": 3,
  "expectedIntegrationVersion": 2,
  "expectedAccountRevision": 4
}
```

示例 UUID 字符串仅表示字段角色；实现测试使用合法真实 UUID。草稿可缺少非焦点步骤的绑定；只有构建焦点 API 请求才要求其目标，目标不足不覆盖已获得的激活/条件判断。定义、trigger、样本限制分别为 256 KiB、64 KiB、128 KiB（输出与状态合计），样本 key 仅允许依赖闭包内 ID，状态仅允许现有四种完成状态；非 success 不得同时提供成功输出。条件样本中的 branchId 必须属于对应节点，scope 与样本状态冲突时报错。

服务端按以下顺序处理：

流程变量扩展：请求可带 sampleVariables 表示节点进入时的完整变量样本；API 的 assign 预览另用 sampleResult 表示当前 API 响应。所有样本（输出、状态、变量、当前响应）合计仍最多 128 KiB，sampleResult 不混进仅允许祖先 ID 的 sampleOutputs。变量名称/类型、当前响应适用类型均需验证，不执行真实 API。存在祖先写入却缺 sampleVariables 时不能以初始值冒充当前值；无祖先写入可按 trigger 初始化。

运行信息扩展：workflow 模式可带 sampleRunMetadata，完整填写 triggeredAt、scheduledFor（允许 null）、timezone；服务端派生 businessDate，按节点第 2.8 节验证，并在 runMetadataPreview 返回四项样本值。解析运行来源或相关初值需要它却未提供时返回 unavailable，不读取当前时钟；无样本则省略 runMetadataPreview。该对象与其余样本合计仍最多 128 KiB，不占用 stepId 样本 key；code_inputs 拒收它且不返回运行信息预览。真实触发接口只沿用 input，不接受这些样本字段覆盖服务端运行信息。

1. 检查版本、限额、类型、图结构、scope、焦点及依赖来源；只对 API 类型检查 API 实体，不要求整个草稿可部署。
2. 建立 trigger、样本输出和显式 status 上下文，不凭样本推断成功。先检查 scope，再按顺序判断旧 runIf；返回 matched/not_matched/unavailable/error。exists/not_exists 遇到实际缺失路径按引擎求值；必要分支选择样本缺失为 unavailable。未激活时停止输入解析，不要求补造不会使用的值。
3. 焦点为条件节点时，用同一求值器评估 IF/ELSE IF，返回 selectedBranchId 与各分支 matched/not_matched/not_evaluated/error；错误不落入 ELSE。数据处理解析 source、执行同一有序操作函数；代码解析命名 input/Schema，经能力与容量检查后执行受限 CodeRunner，实际返回结果用于输出和赋值预览，不接受 sampleResult 伪造自身输出。
4. 焦点为已激活 API 时，用 actionTarget 与版本检查核对目标，不获取凭据；再解析 input，复用 PrepareInput、Catalog.ValidateInput 应用默认值与校验。目标或参数错误不覆盖前面获得的激活/旧条件判断。
5. API 用 BuildRequest/RequestPreview 返回请求摘要；所有类型的样本输入和结果均使用 safejson 限长脱敏。
6. 未激活 API 返回 requestPreviewStatus=unavailable 及跳过原因；激活状态 unavailable/error 时不宣称会执行或跳过。预览缺样本与真实运行错误分开表达。
7. 对本地结果或 API sampleResult，用同一赋值准备函数计算变量候选变更，所有 vars 右值取节点进入时版本。返回 assignmentPreviewStatus=ready/unavailable/error/not_applicable 与 variableChangesPreview；只在样本副本上计算。API 缺 sampleResult 时，请求仍可 ready，赋值预览为 unavailable；失败不得清空配置或调用 API 补样本。

workflow 模式响应共用 stepId、nodeType、activationEvaluation、dataSource=sample、validationScope=workflow_sample、diagnostics；API 保留 conditionEvaluation、requestPreviewStatus、实际取得的 inputPreview/request/目标版本/verified，conditionEvaluation 表达旧 runIf 判断。激活与条件为 matched/not_matched/unavailable/error，请求为 ready/unavailable/error。数据处理返回 outputPreview 和 operationSummaries；代码返回 outputPreview、durationMs、runtimeProfile 和受限日志/行列诊断；条件返回 selectedBranchId 与 branchEvaluations。不适用或未生成的字段省略。样本计算用正常响应承载状态，权限拒绝、版本冲突和非法图沿用 HTTP 错误。

未解析到路径时返回第 8.3 节可定位的 diagnostics，不填空字符串、不伪造值、不自动调用上游 API 获取结果。样本不足诊断仅影响当前预览，不自动成为部署阻断问题。比如上游 status=skipped 且无输出，当前 runIf 要求上游 success 时，应得到 not_matched 和不可用请求预览，而非“缺少上游 id，流程失败”。

所有分支不得调用 Runner.Run、Executor.Action、Auth.Resolve/Verify 或 EnqueueWorkflow，不创建 operation/job，不保存 definition、trigger、样本或预览中的业务数据到审计。现有框架请求审计若记录 POST 元数据，只保留动作和焦点标识，不记录样本正文。

#### 5.9.3 样本输入的体验

开始默认输入自动作为可编辑预览 trigger，用户修改仅影响本次样本。上游样本列表按依赖顺序显示，支持 JSON 对象、数组、字符串、null，不把所有响应限制为对象。

第一版只提供手工样本和 API Schema/example 建议，样本保存在本页内存。历史步骤事件最大 4 KiB，可能脱敏或截断，因此不提供“使用上次结果”一键自动填入功能；用户需要时查看摘要并手工填写有效样本。填写样本不会改变 workflow 默认输入或节点 input。

代码默认按 inputSchema 渲染 sampleInput：计算只用三个数时填三个数即可，不要求完整上游响应。页面明确“仅验证代码计算”，展开“验证上游字段映射”后采用本节的 workflow 样本。null 有明确输入方式，空白不自动变为 null；sampleInput 也计入 128 KiB 样本预算，不能传给真实运行入口覆盖来源。

workflow 时间样本提供触发时间、可空的计划时间和时区控件，服务端返回派生业务日期；只有用户提交的明确样本才参与计算。跨日/夏令时示例与正式运行共用 Go 日期派生逻辑。code_inputs 中的日期只是命名输入样本，不宣称已验证计划时间映射。

已解析业务输入预览与实际运行默认值后输入摘要应一致。为实现此点，第 9.1 节 inputPreview 必须记录 PrepareInput 后的有效输入，并沿用相同校验规则；未应用默认值的模板解析结果不能标为“最终输入”。

### 5.10 账号和集成修复，保持画布上下文

目标/账号选择状态约定：

| 状态 | 用户看到的内容 | 主操作 |
| --- | --- | --- |
| 目标候选加载中 | 集成位置骨架和加载状态 | 不清空已有绑定 |
| 没有 ready 集成 | “此 API 暂无可用集成” | 去集成/认证中心配置 |
| 有集成但没有账号 | 集成正常，账号为空 | 新标签添加账号 |
| 有账号但未验证/验证过期 | 保留账号名，显示原因 | 新标签打开准确账号验证 |
| 账号禁用或已删除 | 保留原引用占位并说明 | 重新选择，不自动替换 |
| 无认证集成 | “无需账号” | 继续配置参数 |
| 刷新失败 | 原选择仍在，状态待确认 | 重试刷新；阻止部署/运行 |

默认修复入口使用同源新标签并设置 noopener，保留画布内存中的未保存输入，不复制认证表单，也不假设现有认证中心支持任意 returnTo 自动跳回。返回画布后点击“刷新可用目标”，或在 focus/visibilitychange 后只刷新选中 API 的目标候选。

新账号出现后明确展示“发现新账号”，用户点击使用才绑定，不根据创建时间或列表顺序自动选择。重新读取 account revision、verification 和 integration targetVersion，不能只改一段“已验证”前端文字。

工作流侧栏不提供拿当前节点直接验证账号的按钮：当前节点可能是 POST 创建/删除 API，而现有 verify 接口可以实际调用所选 API。验证在认证中心使用既有流程，OAuth 授权和凭据修改也继续在那里完成。

### 5.11 API 定义变化、版本与刷新

当前工作流保存的是 API 引用，并不固定“部署那一刻的 API 定义副本”；API 版本是在每次运行快照创建时固定。运行中版本变化会被引擎拒绝。界面不得提示“部署后永远使用旧 API 版本”。

编辑器首次加载按 API UUID 获取当前定义，并缓存该版本与 Schema。回到页面、显式刷新或部署前重新检查当前定义与执行候选；变化时：

- 展示“API 定义已更新”，列出参数新增/删除/类型/default、方法/路径、响应规则或预算变化。
- 保留旧配置值，明确标出不再兼容的字段；用户确认使用新定义后重算本地校验并清除旧预览。
- API 被停用/删除时保留节点，禁用部署和运行，提供查看定义或更换 API。
- 集成地址变化使账号验证过期时，阻止执行并引导修复；只改集成显示名称不错误地要求重新验证。
- 同一个 API 用于多个节点时显示变化影响的全部节点，不只刷新当前侧栏。

前端重新检查只能改善体验，不能代替服务端并发检查。expectedVersion 保证的是工作流版本，不保证 API/集成不会在两次请求之间变化；普通请求预览可使用已有 expectedApiVersion 等字段检测预览期间变化，工作流最终仍以触发事务里的实际 API、目标校验与运行快照为准。

本次不另建部署版 API 仓库，也不承诺原引擎没有提供的“完整请求目标冻结”。如以后要求审阅版本必须与触发版本完全一致，需另行把预期 API/集成/账号版本传入触发事务并扩展快照执行检查，不能仅依靠前端缓存宣称已经保证。

### 5.12 请求与状态更新的实施细节

| 时机 | 请求 | 本地处理 |
| --- | --- | --- |
| 打开已有流程 | workflow detail | 初始化 Definition/Layout，记录两个版本，不用全局 demo 列表猜详情 |
| 展开 API 搜索 | 带 q/system/status/executable 的分页请求 | 独立 query key，不影响已选节点 |
| 选择 API | 详情 + execution-options 并行加载 | 按 API ID/加载代次丢弃过期响应；保留已配置值 |
| 选择集成 | 使用已加载 options | 校验账号归属；失效账号只提示，不替换 |
| 选择账号 | 使用该目标 accounts | 同时显示验证状态和基础地址，更新本地绑定 |
| 点击预览 | literal preview 或 preview-step | 保存本次请求指纹，任何输入/目标/版本变化使其失效 |
| 保存业务与布局 | 单一原子保存请求 | 更新服务端版本和本次提交基线；仅清除已提交修改的 dirty，保留提交后的新编辑 |
| 仅保存布局 | layout PATCH | 更新布局基线，仅清除已提交的位置修改，不更新部署状态 |
| 部署成功 | deploy | 用返回实体更新 version/status/nextRunAt |
| 点击运行 | run | 返回 operationId 后进入只读运行页，不把 operation 当最终结果 |
| 运行中 | operation 轮询 | 仅更新运行态，不改编辑器 Definition/Layout |
| 成功终态 | result | 单独读取最终结果，按权限显示 |
| 查看历史 | operation + view | 不回查当前 API 定义覆盖历史信息；配置编辑会话继续保留在父路由内存 |

工作流详情目前后端已有 GET，但 web/src/api.ts 尚无专用 workflow(id) helper，需补该方法和强类型。execution-options 的类型优先从 API 页提取为共享业务类型，并保持页面权限处理一致；不要复制不同账号有效性条件。

预览缓存指纹包括 graph 版本、stepId/type、variables/assign、input/source/operations/branches/scope/runIf、code/language/runtimeProfile/inputSchema/outputSchema、previewMode/sampleInput/sampleRunMetadata、来源映射、绑定、所有样本及适用的 API/目标/账号版本；模式、变量初值、写入依赖、源码、时间/时区或其他样本改变均使预览失效。仅最新响应可显示为当前预览，失败不清输入，不作为幂等键。

## 6. 前端状态与画布转换

### 6.1 唯一数据源

编辑态持有 workflow 业务字段、Definition 和 EditorLayout。React Flow nodes/edges 由它们派生；拖动只更新布局，连线/汇合原子更新 dependsOn、scope 和受影响来源；侧栏更新对应配置，不另存 React Flow 执行图。

允许缓存派生节点用于 React Flow 交互，但不能把节点 data、侧栏 state、业务 steps 各保存成一套互相同步的持久模型。未完成文本、JSON 语法错误等可以是局部缓冲状态，未应用时阻止误保存或提示未应用编辑。

服务端数据使用现有 TanStack Query/queryClient；编辑态用 useState/useReducer，不另增状态库。所有远端响应按 workflowId、runId 和加载代次校验，防止切换节点后旧响应覆盖新选择。

建议强类型结构：

```ts
type WorkflowDefinition = LegacyDefinition | {
  schemaVersion: 2;
  inputSchema?: WorkflowInputSchema;
  variables?: WorkflowVariableDefinition[];
  steps: (ApiStep | TransformStep | CodeStep | ConditionStep)[];
  output: Record<string, ValueSource>;
};
type EditorLayout = {
  schemaVersion: 1;
  direction: "LR";
  positions: Record<string, { x: number; y: number }>;
};
// 业务版本 version 与布局版本 layoutVersion 独立。
// 用 @trigger / @result 表示虚拟节点；它们不进入 steps。
```

上述为结构示意，v2 ValueSource、scope 和类型字段见[节点执行契约](workflow-node-design.md#execution)。步骤 ID 不允许 @，虚拟 ID 与旧步骤不冲突；@result 显示为“结束”。连线 ID 由端点及稳定分支 ID 生成，不依赖出口顺序或动态序号。

### 6.2 布局规则

Dagre 使用 LR 方向、各类节点实际尺寸和稳定输入次序；条件高度按分支行数计算。结果转为 React Flow 左上角坐标，变更分支后更新端口尺寸及局部间距，不因每次填参数重排全图。

- 首次打开旧定义：没有位置时自动布局，仅产生本地布局修改，不修改定义。
- 新增节点：优先在选中节点右侧放置；位置冲突时做小范围偏移，不重排全图。
- 自动布局是显式操作，可撤销，保留业务声明次序。
- 已保存位置优先；新增或缺失位置的节点补齐，损坏的布局回退为自动布局，业务定义照常加载。
- viewport 缩放与平移是会话状态，不写全局布局，避免每次滚动都保存且影响别人打开页面。首次打开历史默认查看全图，编辑页从历史返回时恢复原视口，不重新 fitView。
- 不需要无限画布白板功能、分组、自由文本标注或多人实时协同。

### 6.3 编辑会话与跨路由恢复

在工作流父路由中持有一个当前编辑会话，按 workspaceId、workflowId（新建时为临时 ID）隔离。使用现有 React state/context 或 reducer；不要为此引入全局状态库、多文档缓存或持久存储。工作流子路由共享会话，运行状态另外保存。

- 配置切换到历史列表、打开运行详情后返回，恢复 Definition、Layout、未应用 JSON/字段缓冲、选中节点、侧栏页签、参数区滚动位置、画布视口和未保存操作历史。
- 新建保存后 replace 到实体路由时，把临时会话迁移到返回的 workflowId，保留提交后新输入；路由变化不能重新初始化整份定义。
- 返回时可后台检查服务器版本，但不能直接覆盖 dirty 会话；检测到变化后进入第 6.4 节冲突处理。运行轮询只更新运行数据。
- 切换到另一个工作流或离开工作流模块前，对未保存内容和未应用缓冲执行离开保护；确认放弃后清理会话。退出登录、切换 workspace 时清理，防止跨身份恢复。
- 查看 API 或修复账号的新标签操作没有离开当前页面，不应触发丢弃编辑确认。页面刷新和关闭仍使用原生离开提示，刷新后只恢复已保存服务端配置；不承诺恢复未保存内容。

### 6.4 保存并发、组合操作与版本冲突

业务定义和布局各持有本地编辑修订号及已保存基线。发起保存时捕获提交内容、两个本地修订号和服务端版本；保存请求未结束时仍可继续填写字段，但同一工作流的保存、布局保存、部署和暂停等写操作串行提交。

1. 提交 A 后继续修改得到 B，A 成功只推进对应服务端版本和保存基线；B 保持在界面并继续标记未保存。不要用 A 的返回实体覆盖 B，也不要无条件清空 dirty、JSON 缓冲或提交后产生的撤销记录。
2. 定义和布局分别判断是否有提交后修改。仅保存布局不得清业务 dirty；原子保存两者后也按各自提交基线处理。失败不推进基线，用户输入保留。
3. “保存并部署”“保存并部署后运行”捕获一次明确编辑修订，并逐步使用上一步返回的服务端 version。在部署或运行前发现本地已新增业务修改时，停止自动后续步骤，显示“已保存较早修改，请保存最新修改后继续”；不能运行 A 却把 B 当作已运行配置。
4. 每一步显示保存中、部署中或提交运行中；前一步失败不继续调用。保存成功而部署失败的调度影响按第 4.10 节显示，运行提交响应不确定时仍按第 9.4 节处理，不能自动重发。
5. 409 时保留本地定义、布局和全部编辑缓冲，提供“查看服务器版本”“复制本地配置”“放弃本地修改并加载”操作。服务器版本在独立只读面板显示，不能先覆盖编辑态再提示冲突；加载覆盖必须是明确的放弃动作。本次不自动合并冲突、不强制覆盖。

复制本地配置仅在用户点击时进行，复制其有权编辑的业务配置和布局；未应用的 JSON 可在原编辑框单独复制，不伪造为已应用定义。不附带运行结果、样本或账号凭据，不写入浏览器持久缓存。

## 7. 存储与版本设计

### 7.1 新增布局列

建议新增迁移 `007_workflow_visual_editor.sql`（实施时确认迁移号未被其他工作占用）：

```sql
ALTER TABLE workflows
  ADD COLUMN editor_layout jsonb NOT NULL DEFAULT '{}'::jsonb,
  ADD COLUMN layout_version bigint NOT NULL DEFAULT 1;
```

增加对象类型和正版本 CHECK、列注释，并接入 `internal/store/store.go` 的 embed 与迁移列表。无新工作流表、无第二份执行 graph。

布局限制：最多 22 个位置，key 只允许当前步骤 ID 和两个虚拟节点；schemaVersion=1、direction=LR、坐标必须有限且绝对值不超过 100000，负坐标允许；总大小上限 32 KiB。服务端白名单投影，不能存凭据、函数、节点 JSX、运行结果或 React Flow 全量对象。

### 7.2 保存语义

| 操作 | version | layoutVersion | 状态与调度 |
| --- | --- | --- | --- |
| 业务定义保存 | 增加 | 布局一并修改时增加 | 回 draft，清空 next_run_at |
| 仅布局保存 | 不变 | 增加 | 保持部署状态、next_run_at 和业务 updated_at |
| 部署/暂停 | 沿用已有增加规则 | 不变 | 沿用当前语义 |
| 运行 | 不变 | 不变 | 固定当次快照 |

使用两个 dirty 标记：definitionDirty 和 layoutDirty。仅拖动时主保存按钮执行布局接口，不把业务保存接口当成布局保存接口。

新建或同时修改业务与布局时，在同一事务内保存两者。创建请求可携带 editorLayout；更新请求携带 version、editorLayout 和 layoutVersion。更新同时检查业务与布局版本，避免“定义保存成功、布局保存失败”的部分提交。

兼容客户端只改业务、未携带布局时，保留仍存在节点的位置，清理已删节点位置；发生布局变化才增加 layoutVersion。v2 图拒绝旧客户端不带 graph 版本的整图覆盖或降级，不能重序列化后静默丢失 type/scope/branches/inputSchema/variables/assign/code/outputSchema/runtimeProfile；旧 v1 更新保持兼容。

布局更新携带 expectedWorkflowVersion 与 layoutVersion；SQL 在同一更新中检查 workspace、未删除、业务版本、布局版本。更新请求的所有节点必须属于已保存 graph。未保存新增节点随业务保存提交，不能提前布局保存。

冲突返回 409，按第 6.4 节保留本地编辑、查看服务器版本并允许显式放弃后加载；不得静默强制覆盖。部署/运行成功后更新返回的业务版本，不使用部署前版本继续保存。业务保存与部署仍是独立事务，保存后停止新的触发，部署失败不自动回滚或恢复旧部署。

### 7.3 快照扩展

加密 Snapshot 增加定义 schemaVersion、inputSchema 和可选 editorLayout；StepSnapshot 保存 type、scope、处理操作、条件分支与来源映射。代码保存源码、input/outputSchema、language/runtimeProfile 及实际 runner 构建标识，升级兼容见代码专项。API 步骤继续固定具体绑定与版本，并补 actionName、systemKey、httpMethod、relativePath、集成/账号显示名称。非 API 步骤不要求 action 字段。历史展示读取当次信息，不用当前名称替代。

同时保存变量声明、节点/出口 assign，以及触发时已按实际输入解析并校验的 initialVariables。各次运行持有独立 vars，执行时不重读当前默认配置，不回写 workflow.input。初始化失败不创建可执行任务或调用 API；运行中的变量更新无需增加变量表/版本服务，仅纳入当前运行预算和事件摘要。

v2 快照另存 runMetadata：triggeredAt、scheduledFor、timezone、businessDate。在初始化变量前统一生成，和快照一起提交；幂等重读、排队和跨日执行保持原值。只读运行 view 可展示这四项以解释业务日期，旧快照缺失时标记未记录。不得从当前时钟、今天的时区配置或步骤 startedAt 补造；详见节点第 2.8 节。

基础地址和完整请求头不用于画布展示；真实认证仍由 authn 服务负责，快照不增加凭据。现有触发输入和业务绑定按原加密机制保存。

所有快照构建入口都要更新：手动入队、runtime 同步/异步和定时入队。更新 scanWorkflow 及全部 SELECT，不能只改列表查询。触发事务内读取的图、布局和展示字段共同构成当次快照；运行过程中不再次从当前工作流读取布局。

老快照缺少展示字段时使用已有 title/actionKey，缺少布局时自动布局，缺少 API 展示信息显示“历史记录未保存”。不回填伪造历史数据。

### 7.4 部署编译及审计的事务边界

代码部署先读取指定工作流版本并在数据库事务外完成 compile 预检，再进入短事务核对版本/图摘要/绑定/运行配置，原子提交部署状态与审计。不能在包裹整个 handler 的 a.audited 内等待共享容量或子进程；仅调整此路由的事务范围，不能丢弃审计原子性。并发编辑使预检失效时返回 409，不部署新定义或自动重做。

草稿保存不执行代码编译；preview-step 不持事务、不存业务数据。startWorkflowRun 和定时入队事务内只验证配置/输入并保存快照，代码环境预检与实际执行在其外完成。具体步骤、预检预算和文件入口见[代码事务边界](workflow-code-node-development-plan.md#transaction-boundary)。

## 8. HTTP 接口设计

以下标注“新增/扩展”的接口已接入首版；权限与实际验证结果见开发验收记录。保持现有 JSON 响应风格与 workspace 隔离。

### 8.1 复用与新增

| 接口 | 状态 | 用途 |
| --- | --- | --- |
| `GET /api/workflows`、`GET /api/workflows/{id}` | 扩展响应 | 返回 editorLayout/layoutVersion，原字段保留 |

| `POST /api/workflows/preview-step` | 新增 | API 请求构建、数据处理/代码样本结果、条件命中预览；不执行 API，代码走受限 worker，见第 5.9 节及代码专项 |

| `POST /api/workflows/preview-schedule` | 新增 | 使用现有规则计算未来三次计划时间；不保存配置、不入队 |
| `GET /api/actions`、`GET /api/actions/{id}` | 复用 | API 搜索及 Schema |
| `GET /api/actions/{id}/execution-options` | 复用 | 集成、requiresAccount 和账号 |
| `GET /api/operations?kind=workflow&workflow={id}` | 修复筛选 | 使用现有分页、状态、日期和游标 |
| `GET /api/operations/{id}` | 复用 | 轮询运行状态与结构化事件 |
| `GET /api/workflow-runs/{id}/view` | 新增 | 当次快照的只读展示投影 |
| `GET /api/workflow-runs/{id}/result` | 复用 | 授权读取成功运行的完整最终输出 |

不新增 /events、独立历史表、完整步骤响应下载接口或通用图编译服务。

`preview-schedule` 请求只含 scheduleType、cronExpression、scheduleTimezone，响应含 evaluatedAt、scheduleTimezone、nextRuns（最多三个 UTC 时间）。服务端使用现有 cronx 和固定间隔计算函数，按服务端当前时间计算，不引入第二套 Cron 解析器；手动触发返回空计划，非法表达式/时区和无法计算未来时间返回可定位诊断。允许 owner/admin/developer，viewer 不发送该 POST；接口不得保存定义、创建 operation/job 或执行 provider 请求。预览不预留执行时间，部署时重新计算 nextRunAt。

部署、暂停和运行的新前端始终发送 expectedVersion。为兼容旧 API 客户端，服务端允许省略；存在时必须大于 0 且匹配，不能把 0 当作绕过校验。界面操作从已加载版本出发，并把预期版本继续传入 Store 的条件更新/触发事务，不能在处理函数里重读最新版本后丢失预期值。旧客户端省略字段仍沿用当前“操作服务端最新配置”的语义，应在接口文档说明该兼容限制。

布局请求示例：

```json
{
  "expectedWorkflowVersion": 8,
  "layoutVersion": 2,
  "editorLayout": {
    "schemaVersion": 1,
    "direction": "LR",
    "positions": {
      "@trigger": { "x": 0, "y": 100 },
      "get_customer": { "x": 340, "y": 100 },
      "@result": { "x": 680, "y": 100 }
    }
  }
}
```

响应返回保存后的布局和两个版本，前端据此推进本次提交的布局基线；若请求期间又发生位置修改，仍保留 layoutDirty。

### 8.2 运行视图接口

运行 view 是管理端只读展示投影，不是直接序列化整个 Snapshot。返回：

- operationId、workflowId、workflowVersion、operation.status 和显示名称。
- editorLayout、定义版本、步骤 ID/title/type、依赖、scope、分支 ID/顺序和处理操作摘要；API 另含 actionName/actionKey/actionVersion/method/path、必要失败策略；代码含声明字段与 runtimeProfile，默认不返回完整源码，历史错误位置不套用当前源码。
- 变量声明、赋值来源及限长脱敏初值摘要；当前值变化由事件呈现，不返回完整 vars 或从今天的默认配置推断历史。
- 默认只返回脱敏且限长的输入模板、触发输入、输出映射摘要，不返回账户凭据、加密字段或完整请求认证信息。
- hasWarnings 从完成事件中读取；老记录无法确认时省略，不凭 status=success 推断没有警告。

展示投影只用于查看，不能作为“编辑历史版本”的保存数据。view 首次加载一次；实时状态用现有 operation 轮询，避免每两秒重新解密并审计快照。

权限沿用现有完整结果的限制：owner/admin/developer 可读 view 和完整最终结果；viewer 可看当前定义与已有脱敏运行摘要，但不通过新增接口读取解密快照。handler 必须显式校验，不能只依赖 allowsAdmin 对 GET 的默认放行。

view 读取记录 `workflow.run_view_read` 审计，不把解密输入写进审计内容。跨 workspace 或不是 workflow 的 operation 返回 404，未授权角色返回 403；记录已清理或无法恢复时提供明确的不可用状态，绝不能回退到当前 graph。

### 8.3 结构化诊断与字段定位

保存、部署、步骤预览、定时预览和步骤事件采用一个小型业务诊断结构，保留既有错误 code/message 及 HTTP 状态约定。管理端错误可在原 details 中增加 diagnostics，预览正常响应及步骤完成事件也可携带 diagnostics；不建设通用诊断框架。

```ts
type WorkflowDiagnostic = {
  code: string;
  stepId?: string;
  phase: "definition" | "branch" | "condition" | "transform" | "code" | "variables" | "input" | "target" | "request" | "response" | "output" | "schedule";
  fieldPath?: string;
  line?: number;   // code 用户源码，1 起始；无可靠位置则省略
  column?: number;
  severity: "error" | "warning";
  message: string;
};
```

- code 使用稳定业务标识，如 missing_reference、invalid_parameter、invalid_binding；message 为可读说明，不承担机器解析职责。首版允许一次返回一个准确错误，不要求重写 Go 校验器为全量收集器。
- 分支、操作错误分别定位 `/branches/{index}/condition`、`/scope/{index}`、`/operations/{index}` 或具体来源 case；稳定 ID 用于引用，JSON Pointer 用当次定义中的准确位置。
- 变量初始化错误定位 `/graph/variables/{index}/initial`，赋值错误定位节点 `/assign/{index}` 或 `/branches/{index}/assign/{index}`；无序读写错误提供相关节点 ID 和变量名，不能通过解析错误文本猜写入者。
- fieldPath 使用 JSON Pointer：有 stepId 时相对于该步骤；没有 stepId 时相对于工作流配置，结果错误以 `/graph/output` 开头，定时错误指向 `/cronExpression` 或 `/scheduleTimezone`。按规范转义 `/` 和 `~`，参数名中的点保持字面值，例如 `/input/customer.id`。
- 复用 executor.FieldError 的字段路径和约束信息，经小型适配函数加上 stepId、phase；图与条件错误在产生处保留结构信息，不靠正则解析 err.Error()。运行侧继续携带诊断到完成事件，供失败节点定位。
- 点击问题后选择节点、展开对应侧栏分区并聚焦字段；输出问题定位结束节点，定时和默认输入问题定位开始节点。错误涉及已删除字段时定位到“未匹配参数”区域，避免跳转到不存在的控件。
- 预览缺样本只是当前预览不可用；使用 phase 和当前操作上下文区分部署问题，不把所有预览 error 一律标成不可部署。旧记录或非结构化错误只显示页面级/步骤级原有说明。
- 诊断不得携带凭据或完整用户值；路径、约束和可读原因足够定位。未知错误保留通用提示与请求 ID，不臆造字段路径。

## 9. 运行事件、状态与结果

### 9.1 统一事件契约

保留既有 OnStep 完成回调，增加 OnStepStart，并给 StepOutcome 增加开始时间、结束时间、耗时、有效输入摘要、独立响应摘要及结构化诊断所需字段。通过一个小型共享记录函数统一同步 HTTP 和异步 worker 的事件属性，不增加通用事件总线或单实现接口。

新事件 attributes 使用 schemaVersion=1 和 eventType，不能依赖中文 message 判断机器状态：

```json
{
  "schemaVersion": 1,
  "eventType": "workflow.step.started",
  "attempt": 1,
  "stepId": "get_customer",
  "stepType": "api",
  "actionKey": "customer.get",
  "status": "running",
  "startedAt": "2026-10-03T02:00:00Z"
}
```

完成事件使用 `workflow.step.finished`，包括相同标识、success/failed/skipped/unknown、completedAt、durationMs、httpStatus、inputPreview、responsePreview、可选 diagnostics 和脱敏错误。字段缺失表示当时未获取到，不虚构空对象。

六节点扩展还包含 stepType，以及适用的 selectedBranchId、skipReason（branch_not_selected / condition_not_met）、outputPreview 和 operationSummaries。API 才有 actionKey/httpStatus/responsePreview；本地节点输出摘要遵守同样限长脱敏规则，不伪装 HTTP 响应。数据处理条数变化、代码 profile/耗时/受限日志与条件命中作为真实执行摘要展示；代码的全部事件预览合计最多 4 KiB，细则见代码专项。

v2 失败事件补 failureClass、phase、errorCode、diagnostics；继续条件按[共用失败契约](workflow-node-design.md#failure-contract)，只有 API 的 api_response 且配置 continue 才继续。代码返回校验/参数/变量/权限/基础设施失败停止；API 响应 Schema 失败与代码输出 Schema 失败分别分类。v1 图/快照保留旧语义，升级提示该差异，不将新限制悄悄应用到旧运行。

变量扩展增加 variableReadsPreview、variableChangesPreview、assignmentStatus（committed/failed/not_applicable）及适用的 apiCallStatus；读写摘要整体各最多 4 KiB，含变量名、写入来源和前后值的脱敏摘要，截断明确标记。failed 不表示部分提交：全部变量保持原值。API 已成功但赋值失败时，stepStatus 为 failed、apiCallStatus 为 success、phase 为 variables，流程停止且不重试。无 assign 时为 not_applicable，不能伪造“已更新变量”。

开始事件在进入步骤逻辑时记录，耗时包括条件检查、参数解析、权限认证和 API 调用；durationMs 用单调时钟计算，UTC 时间用于展示。条件不满足也可产生 started/finished(skipped)，此时没有 API 调用。

API inputPreview 在模板解析并通过 PrepareInput 应用默认值后生成，最多 4 KiB；响应和本地节点输出摘要同限额。数据处理记录已解析 source 摘要，条件记录判断轨迹，均不走 API PrepareInput。输入准备失败不伪造最终输入；先 safejson 脱敏再持久化，超限标记截断。错误文本和 URL 另做敏感内容审查，不能宣称字段名脱敏能识别任何秘密。

响应摘要与供模板引用的成功 Output 分开：

- 拿到真实 provider 响应后，在 CheckResponse 等可能提前返回的检查之前生成独立、限长、脱敏的 responsePreview。覆盖 HTTP 错误、业务成功条件不满足及响应 Schema 校验失败，不能继续只在 outcome.Output 非空时记录摘要。
- 成功响应为 null 或空 body 时使用明确摘要表示真实空响应；没有收到响应时省略摘要并显示“未获取到响应”。失败的 JSON、文本响应按现有安全展示方式处理，不强制解释为对象。
- 失败响应摘要只用于诊断，不写入 templateContext 或成功输出集合；onError=continue 的后续步骤仍不能把失败响应当作成功结果引用。unknown 沿用原有停止且不重放的语义。
- 脱敏与截断发生在持久化之前；同步与异步路径复用同一记录函数。旧记录缺少失败响应时显示“历史记录未保存响应摘要”，不从今天的 API 请求重建。

事件写入失败不自动重试 API，也不把已成功的 provider 调用改成失败；记录服务端错误，UI 显示追踪信息不完整。最终业务结果及 unknown 处理继续由原运行事务负责。

普通 API 的完整请求头、响应头和 HTTP 请求体并没有随工作流步骤保存。本次步骤详情只承诺已解析业务输入及上游响应摘要，不伪装成完整网络抓包。

### 9.2 状态表达

| 节点状态 | 判定来源 | 界面表达 |
| --- | --- | --- |
| pending | 活跃运行，步骤尚未开始 | 等待 |
| running | 开始事件且尚无完成事件，运行仍活跃 | 执行中，显示计时 |
| success | 完成事件 | 成功及耗时 |
| failed | 完成事件 | 失败及错误 |
| skipped | 完成事件及 skipReason | 分支未选中，或历史执行条件未满足；旧记录缺原因时只显示已跳过 |
| unknown | 完成事件 | 结果未知，需核查上游 |
| not_run | 终止点可确认且在其后未开始 | 未执行 |
| unavailable | 终态仍存在事件缺口，或老记录缺少追踪 | 追踪信息不完整 |

这些是画布状态，不新增 operation_runs.status 数据库值。unknown 终态下未完成节点不能继续无限显示 running，也不能批量推断为 failed。

依赖线表达先后约束，不保证上游成功。旧 runIf skipped 和 API onError=continue 仍由后续自行判断，不自动关闭下游；v2 未选分支按 scope 跳过专属节点，公共汇合节点等待有效前驱后执行一次。UI 必须依据后端 skipReason 和实际事件，不能仅按某个前驱 skipped 涂灰整个下游。

开始节点表示输入准备；结束节点仅在最终映射成功后显示成功。执行步骤均成功但映射失败时，保留其成功状态，在结束节点显示映射错误。

运行整体 status=success 但 hasWarnings=true 时展示“完成，部分步骤失败”，保留失败节点；不能改写成数据库不存在的 success_with_warnings。

### 9.3 轮询

- queued/running 时每约 2 秒请求 operation；请求完成后再安排下一次，不重叠轮询。
- 最终结果只在成功终态读取一次；最终 output 空对象仍属于有效结果，不按真值判断。
- 切换 runId、卸载、退出登录时清理定时器并丢弃过期响应。终态停止轮询。
- 429/网络错误使用有限退避到最多 10 秒，并显示“更新失败”；恢复后补读事件。403/404 停止并提供说明。
- 事件按 sequence 排序并按 id/sequence 去重；新事件优先，兼容旧事件 attributes.status/stepId，无 schemaVersion 时不凭 message 编造开始时间。
- 页面隐藏时暂停高频轮询，恢复可见立即刷新；不会因画布节点位置变化重新创建轮询。
- 老记录无 durationMs 显示“未记录”，不根据相邻事件时间推算准确耗时。

### 9.4 运行与历史的用户流程

运行按钮仅针对已保存且已部署版本。definitionDirty 时禁用直接运行，提供“保存并部署后运行”的明确顺序；不运行旧版本后把新画布着色。layoutDirty 可先保存布局再运行，确保进入快照的位置一致。

按钮点击期间锁定重复提交；若响应丢失不自动重发可能有副作用的运行请求，提示查看运行历史确认。运行列表显示来源（手动/定时/runtime）、版本、状态、开始时间、总耗时和请求 ID，支持现有游标加载。

选中运行后跳转只读详情；配置画布按第 6.3 节在父路由会话保留未保存状态，不被轮询覆盖，返回时恢复侧栏与视口。点击失败节点定位步骤详情和结构化诊断，可查看已保存的失败响应摘要。终态不显示续跑/重试按钮；“再次运行”表示从头执行当前已部署版本，需要明确显示版本，不能宣称按老快照重放。

运行时输入使用第 4.9 节字段表单，展示本次实际提交对象及其与默认输入的关系。运行页提供“定位执行中步骤”；仅用户操作触发定位，不在每次状态更新时自动居中。步骤完成后保持用户当前选择，最终映射失败则在结束节点和问题摘要中共同定位。

## 10. 权限、隐私与兼容

### 10.1 权限矩阵

| 功能 | owner/admin | developer | viewer |
| --- | --- | --- | --- |
| 查看当前工作流 | 是 | 是 | 是 |
| 编辑、保存布局、部署、暂停、运行 | 是 | 是 | 否 |
| 步骤请求预览、计划时间预览 | 是 | 是 | 否 |
| 脱敏运行摘要与已有事件 | 是 | 是 | 沿用现有只读权限 |
| 新增解密历史画布接口 | 是 | 是 | 否 |
| 完整最终结果 | 是 | 是 | 否 |

前端禁用与后端检查同时存在。运行视图不新增 runtime token 的发现或查询权限；现有 `/v1` policy、幂等、绑定检查和错误结果语义保持不变。

第 5.1 节的标识解析修正只保证各种 API 引用走同一权限检查，不增加授权范围。

类型扩展后，发现/预检检查图内所有 API 节点（包括备用分支）的权限；本地节点不要求虚构 action 授权，也不能被当作绕过整个工作流权限的入口。所有 API 实际调用仍经过原执行授权与绑定检查。

v2 同时校验至少一个 API；运行开始、各激活节点执行前及最终结果发布前共用运行身份检查，代码/数据处理/条件也受 Token 过期/撤销约束。API 再校验 action/账号，控制面手动/定时沿用显式 principal。身份拒绝立即停止，不受 onError=continue 影响；具体约定见[本地节点授权](workflow-node-design.md#local-node-auth)。

### 10.2 数据使用边界

真实认证在 authn/executor 中处理，不进入节点 data、布局或浏览器持久缓存。编辑配置和缓冲只保留当前工作流父路由会话内存，运行数据使用独立查询状态；不把完整 graph/input/output 写入 localStorage 或 sessionStorage。页面刷新依靠已保存服务端配置，切换 workspace/退出登录清理编辑会话及相关查询。

safejson 只保证已知敏感字段名称脱敏，不等于所有业务数据已匿名化。摘要在 UI 使用“脱敏摘要”，不使用“绝对安全”。复制按钮只复制当前已展示的授权内容。

保存/部署等工作流审计不再序列化整个 saved 对象。用 workflowAuditSummary 白名单记录 ID、版本、变更节点/类别、代码摘要标识及字段名/类型，不记录源码、固定参数、默认输入、样本、完整变量或任意说明文本。before/after 均投影再限长脱敏，不能只改运行日志；完整约定见[源码审计投影](workflow-code-node-development-plan.md#audit-projection)。定义读取权限沿用现有规则，不把定义表或旧审计宣称为已加密/已清理。

最终完整结果沿用当前受限解密接口，与事件摘要明确区分。保留期结束后显示记录不可用，不尝试从日志恢复数据；本次不增加无限期历史存储。

### 10.3 兼容要求

- 老 graph 不需要迁移为 React Flow 格式；第一次打开自动生成画布。
- 无 schemaVersion 按 v1；新增能力完整升级 v2，保留旧 runIf 字面量及单步跳过语义。Store 重序列化、快照和旧客户端更新限制见[版本兼容规则](workflow-node-design.md#execution)，禁止丢失新字段或无提示降级。
- v2 保留 vars 命名空间；旧 v1 可存在名为 vars 的步骤，必须按旧语义读取。升级检测冲突并展示节点/引用原子改名方案，不能把旧步骤结果默默当作运行变量。
- UUID 和历史 action key 都能解析；API 被删除时保留节点错误，不替换到同名新 API。
- 非 JSON/空响应可通过整个步骤引用使用；字段选择器不提供虚构对象字段。
- 未建 Schema、混合模板、数组和特殊路径可以走高级 JSON，不丢失配置。
- 老运行没有布局、名称或耗时可以查看已有真实信息，并标注未记录。
- 旧客户端不发送 layout 时不清空布局；新增字段不改变现有 runtime 返回结构。
- 历史展示不执行 API、不解析认证、不要求原账号仍然有效。

### 10.4 执行器生命周期与发布

在 cmd/apihub/main.go 创建每进程唯一 CodeRunner，通过 HTTP/后台依赖注入复用；NewWorkflowRunner 不新建容量闸门，编译/预览/同步/后台共用进程限额。各次运行的 input、vars、Runtime 保持隔离。

容量接纳按[正式执行优先规则](workflow-code-node-development-plan.md#capacity-policy)：总并发 C≥2 时交互合计最多 C−1，正式等待者优先；C=1 时正式含代码流程登记期间不接纳预览/部署编译，已有交互需在首个业务 API 前等待清空。交互忙时立即返回明确诊断且不自动重发；正式步骤仍可能因正式负载或总预算而失败，不能承诺无排队或自动续跑。capabilities 展示有效策略，UI 保留繁忙请求对应的配置和样本。

all/api/worker/scheduler 按[部署矩阵](workflow-code-node-development-plan.md#deployment)检查，构建脚本、配置示例、非特权服务启动和新旧实例切换同批交付。API 的本地能力不能代表后台；运行开始前检查固定快照所需 profile/环境，失败时不调用业务 API，实际节点执行时再次检查。预检只报告配置诊断，不伪造目标代码节点已运行或耗时。

首次开放 v2 前让所有读取/执行进程升级并退出旧实例，新能力开关默认关闭；不可通过删除新字段回退。关闭新触发不等于取消已接受任务，需保留兼容执行构建直到排空。具体启动器必须在阶段零交付实际配置与验证，不能只靠独立进程或文档文字宣称隔离有效。

能力开关的发布步骤同时交付调度维护命令：所有调度实例停止新入队后，以同一 resumeAt 重排受影响已部署流程的过期计划，成功后才恢复调度，不补跑关闭期间的任务。不自动恢复 paused/draft/disabled，不改已有任务快照；批次跳过、状态提示及分页/重入规则见[调度开关契约](workflow-code-node-development-plan.md#schedule-gates)。

## 11. 响应式、键盘与离开保护

- 桌面验证 1440×900、1280×800；编辑区填满可用高度，保留导航和顶部操作，底部面板可折叠。
- 平板/窄屏在侧栏打开时采用抽屉，不同时挤出三列；画布仍可查看和缩放。
- 手机验证 390×844：默认步骤列表及全宽配置抽屉；通过前置步骤、分支出口、在此汇合操作修改同一 dependsOn/scope，无需拖线。处理操作和 ELSE IF 支持按钮排序，保留可切换的只读图视图。
- 节点可键盘聚焦、选择、打开配置。增删依赖不要求拖拽；提供侧栏前置步骤选择。
- Delete/Backspace、撤销重做只在画布获得焦点且没有输入控件编辑时生效；不能删除正在输入文字的节点。
- Escape 关闭面板并把焦点归还打开它的按钮；操作结果用 role=status/alert 通知，不只改变颜色。
- 错误列表点击定位节点和字段，首个错误可聚焦。
- 沿用 useUnsavedChanges，但当前只拦截页面关闭和普通链接点击。实现时核对路由模式，补程序导航和浏览器返回的保护，不直接假设当前 BrowserRouter 支持 useBlocker。同一工作流内配置与历史往返通过父路由会话保留编辑，无需每次确认放弃；真正离开编辑会话才提示。
- 普通同源新标签链接不触发丢弃确认；离开保护应检查目标窗口和修饰键，不能拦住文档约定的 API/账号修复入口。
- 业务编辑未保存时明确提醒；布局未保存时显示轻量状态。保存请求未完成不能把 dirty 提前清空，返回成功也必须按提交基线保留之后的新编辑。
- 对 10/20 个节点的长流程，侧栏和底部面板打开后仍可查看全图、通过步骤列表定位任意节点；键盘焦点和被定位节点不能落在遮挡区。

## 12. 实施拆分与文件计划

### 12.1 前端建议结构

```text
web/src/pages/workflows.tsx                 列表，移除旧编辑/运行弹窗
web/src/pages/workflow-editor.tsx           页面、加载、保存、部署、运行编排

web/src/pages/workflow-inspector.tsx        API/绑定/处理操作/代码配置/条件分支/输入输出侧栏
web/src/pages/workflow-model.ts             类型、转换、引用与本地校验函数
```

这是职责划分，不要求提前生成所有空文件。小组件留在所属文件，避免一个按钮一个文件。节点状态和运行详情可先放 workflow-run.tsx，足够复杂时再拆。新增 @xyflow/react、@dagrejs/dagre 和经阶段零验证的按需加载代码编辑器等确有需要的依赖；React Flow UI 按需复制源码，不安装整套 Demo。代码后端另新增固定 worker 构建目标，文件职责详见代码专项第 6 节。

工作流父路由和编辑会话可以先放在 workflow-editor.tsx，以现有 Context/reducer 供编辑及运行子路由访问；不提前拆独立状态管理包。诊断类型和映射优先放在 workflow-model.ts，服务端复用已有 FieldError 并补最小工作流上下文。

### 12.2 阶段零：交互原型验证

先用“开始 → 查询客户 → 创建订单 → 结束”、多 ELSE IF → 分支 API → 公共数据处理 → 结束，以及 20 个混合执行步骤，验证添加、字段映射、处理操作、分支出口/汇合、侧栏配置、错误定位及手机步骤列表。原型使用最终 React Flow、现有 UI 和受控样本，可逐步成为实际编辑器，不建独立演示应用。

桌面覆盖 1440×900、1280×800，手机覆盖 390×844；复杂样本包含长标题、多根节点和合流。检查侧栏/底部展开后的可见区域、按钮主次、参数控件尺寸和键盘路径，再确定节点尺寸、侧栏宽度、缩放边界及操作路径。

保存桌面/手机截图和交互问题记录，修正阻断问题后进入完整工程实现。原型通过只表示交互已验证，不表示后端、权限、真实请求或服务部署已验收。

代码部分同时完成[专项阶段 A](workflow-code-node-development-plan.md#development)：多来源输入、main 编辑、返回字段传递的 UI 原型，以及真实 goja worker/受限启动器、超时/内存/进程回收验证。隔离能力未验证不能开启代码执行，不用前端样本模拟替代。

### 12.3 阶段一：节点执行能力与可视化配置

1. 先实现 v1/v2 类型、四种步骤、inputSchema/nullable、variables/assign、scope 和旧定义无损转换；同步更新绑定解析、所有入口与快照保真、runtime 预检、至少一个 API 校验，处理 vars 冲突。code 保存源码、输入/输出 Schema 与 profile，不把快照推迟到阶段二。
2. 接通共享 CodeRunner、分类失败、运行身份与环境预检、事务外部署编译/短事务审计，先完成 API1 → API2 → 代码共同计算 → API3 → 结束；此链不依赖流程变量/分支，验证同步/异步/定时及两模式样本，API3 参数与调用次数准确。
3. 简单链通过后，再实现变量初始化/读写依赖/批次赋值、数据操作、IF/多 ELSE IF/ELSE、scope/汇合；允许条件承接汇合并补结束收口；覆盖赋值失败停止、代码失败不重放、旧 runIf/unknown/v1 兼容和全部复杂场景。接入 kind=run、触发时冻结的 runMetadata 和时间样本，先生成运行信息再初始化变量。
4. 增加布局迁移、扫描、原子保存与布局接口，覆盖部署后拖动不回 draft；完善六类 React Flow 节点、分支端口、结构化汇合、复制删除、撤销重做和响应式。
5. 实现共用来源/赋值选择器、流程变量表、按分支取值、操作列表、代码编辑/返回字段、条件出口赋值、结束映射、输入 Schema 与 JSON。按第 5.6–5.12 节及代码专项完成节点/赋值样本预览、代码能力探测、默认值、定时预览、账号修复和字段定位。
6. 增加 expectedVersion，接好保存/部署/暂停及组合操作；保护保存后继续编辑，准确显示停止触发影响，删除重复旧表单。
7. 完成父路由会话、历史往返恢复、版本冲突、旧客户端防降级、草稿、权限和离开保护。
8. 完成正式执行优先及 C=1 行为、能力关闭时禁用定时项的非阻塞跳过、恢复重排 Store 函数与维护命令；能力和计划提示同步 UI，操作步骤纳入发布文档。

启用 UUID 保存前完成 runtime 发现与权限预检的标识解析适配，确保管理端、同步、异步和逐步骤检查识别同一 API。

阶段一须能无损打开旧工作流，并通过真实执行链验证六类节点、场景 1–14、15 的批量接口路径及代码 C1–C6；代码按专项阶段 B–D 推进。仍须完成阶段二的运行追踪和整体验收才能宣布交付。

第 2 项是独立的纵向里程碑，先用测试 provider 与真实受限 worker 验证，再扩展后续能力，不能以画布 mock 或浏览器 JavaScript 计算替代。复用已有 json.Number、JSON Schema 和 FieldError；共享小型校验函数，不新增第二套 Schema 引擎或无界草稿缓存。未实现类型拒绝部署，完整交付前不开放未验证的新能力。

### 12.4 阶段二：运行可视化与历史

1. 统一四种步骤事件及两条运行路径，记录 branchId/skipReason/处理/代码/变量变更摘要，区别 API 成功与赋值失败，独立保存响应并透传诊断。
2. 扩展加密快照展示元数据，新增受限 view 接口及审计。
3. 修复现有运行 SQL 的 workflow 筛选，复用分页构建历史。
4. 完成只读运行图、状态投影、计时、步骤摘要、错误定位与最终结果，提供执行中步骤定位且不抢用户视口。
5. 覆盖配置修改后的历史查看、软删除、旧事件、unknown 和数据清理后的状态。
6. 从工作流列表和全局运行记录增加跳转，保证同一业务记录只有一套详情实现。

### 12.5 适合 AI 开发的任务约束

每个任务以行为与验收用例为单位提交：阶段零先验证交互，正式工程再按模型与存储契约、UI 编辑、事件与历史推进。AI 不得为了实现某个视觉效果改变依赖、重试或条件语义。

每次改动写清：影响哪些文件、业务协议是否变化、已运行哪些检查、剩余哪些验收。审查必须关注跨系统绑定、丢失未知 JSON、图与历史版本混用、布局触发业务保存、漏更新同步/定时路径这五类问题。

不预建插件注册中心、通用 Schema 解释器、通用编译平台或前端执行引擎。固定六类节点，代码复用 goja，仅新增必要的受限 worker；处理操作和多个 ELSE IF 是节点内部配置，按分支传值是共用映射能力。

| UI 状态 | dirty 下不能误运行；no-auth 不要求账号；失效绑定不替换；部署后版本刷新；轮询停止和旧响应丢弃 |
| 保存与编辑恢复 | 保存 A 期间编辑 B，返回后 B 仍 dirty；布局与定义各自基线；组合操作中发生新编辑则停止后续部署/运行；部署失败显示停止新触发；409 保留缓冲；新建路由迁移及历史往返恢复；退出身份清理 |
| 运行投影 | 最终映射失败、成功带警告、终态事件缺口、无耗时记录；不凭缺失事件制造成功 |

迁移与 Store/API 测试需要真实 PostgreSQL；涉及队列和权限的集成检查需要 PostgreSQL/Redis 与测试 provider。纯前端 mock 不能替代这些检查。

### 13.3 本地检查与服务更新的区别

开发后运行当前项目的 `npm --prefix web run check`、相关 Go 包测试、`go build ./...`、`git diff --check`；DB/队列检查运行 `scripts/test-integration.sh` 并记录最终退出状态。

不要用“构建通过”替代真实执行验收。前端构建会生成 `internal/webui/static` 嵌入资产；更新实际服务还需要重建 Go 二进制并按已有授权重启准确的服务。不得自行停掉未知进程、占用端口或把本地 mock 结果称为生产已上线。

本文编写期间未安装新依赖、运行这些实现检查、修改数据库或更新服务。后续验收记录应逐项填写“通过/未运行/阻塞原因”，不要预填通过。

## 14. 风险与处理决策

代码专项风险包括无限计算、内存压力、输入/返回精度损失及 runner 版本不匹配，按[受限执行与预算](workflow-code-node-development-plan.md#runtime)验证；隔离未就绪时不启用执行，不回退主进程。代码样本执行不触发 API，但仍消耗资源，必须共用容量控制。

| 风险 | 处理 |
| --- | --- |
| React Flow UI 样式与现有组件重复 | 按需采用 Base Node/Status 等必要部件，适配现有 token，不初始化第二套全局主题 |
| 看上去分叉却没有并行 | 图说明和运行状态明确依赖与串行次序，不提供并行控制 |
| 两套编辑状态相互覆盖 | Definition 单一数据源，JSON 为应用前缓冲，运行 state 单独存放 |
| 只加画布条件却无法隔离后续路径 | 后端显式 scope 与分支优先检查；多出口/空分支/嵌套汇合验收 |
| 汇合引用未执行分支或重复调用公共 API | 按命中分支懒解析，拓扑串行只处理公共节点一次 |
| 旧模型重序列化丢失新字段 | v2 类型、Store/快照/入口一并扩展；拒绝旧客户端降级覆盖 |
| 变量读写无序或误用旧值 | 读写集合与依赖/互斥校验，显示保留原值的出口，API 成功后的赋值错误停止 |
| 更新变量污染开始输入或其他运行 | 每次独立初始化及不可变复制，不回写默认输入；记录限长脱敏变更 |
| 把当前页计数或批量节点误称全量/循环 | 样本与界面明确集合范围；不自动翻页，不隐式逐项调用 |
| 历史 API/账号名称漂移 | 触发时固定展示字段，旧记录标缺失 |
| 保存布局暂停调度 | 独立布局接口与版本，回归检查 next_run_at |
| 保存业务配置意外停止新触发 | 提前说明保存影响，提供保存并部署；部署失败显示准确状态；不自动保存业务配置 |
| 保存响应覆盖后续编辑或历史往返丢内容 | 父路由编辑会话、分开保存基线，覆盖慢网与路由恢复验收 |
| 错误无法定位或失败请求无响应摘要 | 小型结构化诊断，响应摘要独立于成功 Output |
| 预览先解析输入导致本应跳过却报错 | 对齐条件优先顺序，条件与请求预览分别表达结果 |
| 长图无法完整查看或节点被侧栏遮挡 | 全图与可读节点定位分开，20 步原型及步骤列表验收 |
| 日志漏写导致虚假状态 | 结构化事件与 unavailable 回退，业务结果仍以运行终态为准 |
| 事件泄露输入或认证 | safejson 预览、限额、显式读权限、无凭据布局；不展示未保存的完整网络信息 |
| 上游已有副作用但界面断网 | 不自动重复 POST run；去历史确认，unknown 不重试 |
| 新框架兼容性问题 | 安装时固定经过验证的版本并提交锁文件，检查 React 19/Tailwind 4 的 CSS 顺序及真实构建 |

本次方案不依赖 UI 承诺改变执行行为。完成标准是普通用户能顺畅配置并运行真实 API 流程，开发者能够从图上定位问题，历史与权限均准确，而不是仅得到一张可拖动的图。
